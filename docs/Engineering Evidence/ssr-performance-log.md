# SSR / 效能改造量測紀錄

跨變更累積的效能量測紀錄。每次 SSR 或效能相關改造都在對應頁面的表格**新增一列**；
量測有誤時不刪除舊數據，在「更正紀錄」說明原因並補上新數據，原始樣本保留在附錄。

## 結論摘要

| 頁面 | 改動 | 主要結果 |
|---|---|---|
| `/lottery-hall` | 彩池首次抓取改用 `useAsyncData`（公開資料，無需登入） | 首次出現真實數字 **486ms → 226ms**（約 2.1 倍）；TTFB 17ms → 20ms，本機幾乎無代價 |
| `/admin/reports` | 報表與權限檢查改用 `useAsyncData` + `useRequestHeaders(['cookie'])` | 第一版反而變慢（390ms → 485ms），根因是 hydration 時重複打權限 API；修正後 production build **p50 186ms / p90 312ms** |

> ⚠️ 尚待補齊：兩頁的「改造前」基準目前只有 `nuxt dev` 數據。要跟 production build
> 的改造後數據比較，需用 `git worktree` 取出改造前版本，在 production build 下重新量測。

## 量測方法

- **腳本**：`test/perf-ssr-lottery-hall.mjs`、`test/perf-ssr-admin-reports.mjs`（Playwright）
- **指標**
  - **TTFB**：送出請求到收到第一個 byte
  - **首次真實數字**：目標元素第一次出現非空、非 0 的真實數字，代表 CSR waterfall 的實際成本
  - **settled**：目標元素文字連續 300ms 不再變動；包含數字動畫時間
  - **LCP**：Largest Contentful Paint
- **環境**
  - `dev`：`npm run dev`（port 6100）
  - `prod`：`nuxt build && node .output/server/index.mjs`（port 6200）
- **已知侷限**：settled 以「連續 300ms 不變」判定。若 JS 下載與 hydration 超過 300ms，
  腳本可能在 `onMounted` 啟動動畫前就判定穩定，造成部分樣本偏快、呈現雙峰分布。
  這個指標主要反映動畫時長（設計常數），不建議當成 SSR 效益的依據。

## `/lottery-hall`

| # | 版本 | 環境 / 樣本 | TTFB | 首次真實數字 | settled | LCP | Commit |
|---|---|---|---|---|---|---|---|
| 1 | 改造前（`onMounted` 抓取 + 4 秒動畫） | dev / 5 次中位數 | 17ms | 486ms | 4448ms | 296ms | `55e300f~1` |
| 2 | SSR 首版（無首次動畫） | dev / 5 次中位數 | 20ms | 226ms | 226ms | 336ms | `55e300f`、`363460a` |
| 3 | 首次揭示動畫：從 90~95% 起跑，4000ms | dev / 8 次 × 2 輪 | — | — | ~4483ms | — | 中間版本，未單獨 commit |
| 4 | 首次揭示動畫：從 90~95% 起跑，800ms | dev / 10 次中位數 | — | — | 1298ms | — | `6b09cf9` |
| 5 | 首次揭示動畫：從 80~90% 起跑，2000ms（**目前版本**） | dev / 10 次中位數 | — | — | 2513.5ms | — | `c49bc57` |

**解讀**

- SSR 本身的效益看「首次真實數字」：486ms → 226ms。
- 第 2 列 settled 從 4448ms 降到 226ms，主要是因為拿掉了 4 秒動畫，不是 SSR 的功勞。
- TTFB 幾乎沒變，是因為彩池 API 都是同一個 Nitro process 內的記憶體操作。
  若改接外部服務，SSR 必須等資料回來才送出 HTML，TTFB 的代價會明顯增加。
- 第 3～5 列是在 SSR 之後補回首次載入的數字動畫：
  - 從 0 起跑會造成「正確數字 → 歸零 → 爬回」的閃爍，改成從接近目標值起跑。
  - 起跑點不影響 settled 時間。ease-out 曲線的尾段決定整數何時停止變動，所以另外縮短首次揭示的動畫時長。
  - 800ms 的版本肉眼幾乎看不出在跳動，最後選 2000ms + 80~90% 作為折衷。
  - 10 秒輪詢的數字更新仍維持 4000ms。

## `/admin/reports`

| # | 版本 | 環境 / 樣本 | TTFB | 首次真實數字 | LCP | Commit |
|---|---|---|---|---|---|---|
| 1 | 改造前（Shell 權限檢查與報表皆在 `onMounted`） | dev / 5 次中位數 | 12ms | 390ms | 384ms | `fa7bffb~1` |
| 2 | SSR 首版 | dev / 5 次中位數 | 25ms | 485ms | 460ms | `fa7bffb` |
| 3 | 修正 hydration 重複請求 | dev / 5 次中位數 | 47ms | 280ms | 248ms | `f17b143` |
| 4 | 同上 | **prod / 20 次** | — | **p50 186ms / p90 312ms** | — | `f17b143`、`6b09cf9` |

**解讀**

- 第 2 列變慢的原因：`AdminShell.vue` 的 `guard()` 在 client hydration 時先 `resetAdminAuth()`，
  把 SSR 透過 `useState` 帶過來的狀態清掉，再從瀏覽器依序重打 `/api/me`、`/api/admin/me`。
  頂層 `await` 讓 hydration 必須等這兩次往返完成。
- 第 3 列加上 `nuxtApp.isHydrating` 判斷，只在 hydration 當下跳過重打；client 端切換後台頁面時仍會重新驗證 session。
  Playwright 確認重新整理時瀏覽器端這兩支 API 從各 1 次降為 0 次。
- 第 3 列的 5 次樣本呈雙峰（`[280, 697, 240, 649, 202]`），因此改用 production build 跑 20 次（第 4 列）。
  prod 下 18/20 筆集中在 168~297ms，雙峰沒有重現，推論是 dev 模式的 Vite 即時編譯造成的。
  另有 1 筆 5160ms 離群值，尚未追查原因。
