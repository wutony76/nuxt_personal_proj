## Context

- `add-game-history` 已建立 game-hall 小遊戲的完整架構：client 頁面自包含（engine class + reactive 鏡像 snapshot）＋ `useGameHistory`（A/B 雙模式）＋ server 端 `RETRO_GAME_BASE`（共用基底＋每款遊戲一個服務檔＋每款遊戲一組 API 路由資料夾）。
- 現有八款遊戲裡，PONG 是唯一的「多局賽制」例外，其餘都是「單次連續衝分，開放式無上限」。MINESWEEPER 是本次第二個例外，但形式不同於 PONG（PONG 是「同一種局面重複打 N 次」，MINESWEEPER 是「難度遞增的 5 個不同局面依序過關」）——這是本次架構首度出現的「關卡制（level progression）」，需要在 design 中明確記錄，避免跟既有慣例混淆。
- 現有八款遊戲都以「持續 tick 驅動的 physics/動畫迴圈」為核心（`setInterval` 每 16ms 呼叫一次 `engine.step()`）；MINESWEEPER 本質上是回合制的離散狀態機（玩家點擊才會改變棋盤狀態，格子本身不會自己動），只需要一個每秒跳動一次的計時器用於 HUD 顯示與最終計分，不需要 tick-driven physics。這是本次架構首度出現「非連續動畫」的遊戲。
- 現有八款遊戲全部以鍵盤為主要操作（方向鍵／WASD／空白鍵）；MINESWEEPER 是經典的「點格子」玩法，以滑鼠左鍵／右鍵（或觸控＋模式切換）為主要操作，是本次架構首度以指標裝置為主要輸入的遊戲。
- 現有八款遊戲的計分方向都是「越久／越多分越高」（開放式無上限，或 PONG 的勝場數）；MINESWEEPER 依使用者需求是「時間越短分數越高」，方向相反，且因為關卡數固定（5 關）、每關分數有明確上下界，MINESWEEPER 的 `score` 是本次唯一「有明確理論上限」的計分模型，不是開放式無上限。

## Goals / Non-Goals

**Goals:**
- 提供一款經典踩地雷玩法：翻格／插旗／連鎖展開／首格必安全，5 個難度遞增的固定關卡。
- 首次導入「關卡制」：過關才能進入下一關，任一關踩雷則整場結束，分數為已過關卡的加總。
- 「時間越短分數越高」的計分方向，且分數有明確理論上限（5 關基礎分加總），跟現有遊戲的開放式計分做出區隔。
- Server 端、client 資料層、game-hall 入口完全比照既有八款遊戲的慣例逐一擴充，不引入新的資料庫或跨遊戲共用邏輯。

**Non-Goals:**
- 不做關卡選擇／跳關（玩家只能從第 1 關依序往下打，不能直接挑關卡 5）。
- 不做無限關卡／隨機關卡生成器（固定 5 關，每關的棋盤大小與地雷數是寫死的常數）。
- 不做花色主題／自訂難度／自訂棋盤大小等自訂選項。
- 不做「踩雷後倒扣分數重來」或「復活」機制：踩到雷即整場結束，比照 Non-Goals 慣例維持單次挑戰的清爽度。
- 不引入資料庫；server 端持久化沿用專案現況的 in-memory 作法。
- 不做遊戲重播、不儲存完整過程，只存結算後的摘要（分數、等級／關卡數）。

## Decisions

1. **首度引入「5 關關卡制」，而非沿用其他遊戲「單次連續衝分」或 PONG「同局重複 N 次」的既有模式**
   - 理由：使用者明確要求「關卡設計 5 關」；踩地雷本質上適合「難度遞增的固定關卡」呈現方式（棋盤變大、地雷變多），跟 PONG 的「同一種局面重複打」不同，也跟其他遊戲的「同一種玩法無限打下去」不同，因此是本次第二個架構特例，需要獨立的關卡狀態（`currentLevel`／`levelCleared`）。
   - 做法：`LEVELS` 為長度 5 的常數陣列（每關：棋盤寬高、地雷數、基礎分、每秒扣分、保底分），頁面內用 `currentLevelIndex` 追蹤目前第幾關，過關時把該關分數計入 `totalScore` 後自動進入下一關（比照 PONG `finishRound()` 之後自動進入下一局 READY 的既有做法，但這裡不需要 READY 倒數，改成簡短的「LEVEL CLEAR」過場後直接生成下一關棋盤）；任一關踩雷則呼叫既有的 `finishGame()` 流程，以目前 `totalScore`（已過關卡的加總）結算寫入紀錄。
   - 替代方案：讓玩家自由選關（比照關卡選擇畫面）——放棄，超出這次「5 關循序漸進」的需求範疇，且需要額外的關卡解鎖狀態管理。

2. **首度引入「非 tick-driven」的回合制引擎，只用計時器做 HUD 與計分，不做連續 physics**
   - 理由：踩地雷的棋盤狀態只在玩家點擊時改變，格子本身沒有連續運動，若沿用其他遊戲「`setInterval(step, 16ms)` 驅動 physics」的既有慣例會是不必要的過度設計；只需要一個每秒 tick 一次的計時器更新「目前關卡已花費秒數」的 HUD 顯示，實際遊戲邏輯（翻格、連鎖展開、插旗、勝負判定）全部在點擊事件的處理函式裡同步完成，不需要每 16ms 檢查。
   - 做法：`MinesweeperEngine` 提供 `reveal(row, col)`／`toggleFlag(row, col)` 兩個由點擊事件呼叫的方法，內部同步完成連鎖展開與勝負判定並回傳結果；頁面另外維護一個 `setInterval(1000ms)` 只更新「經過秒數」顯示與計分用的時間戳記，不驅動任何棋盤邏輯。
   - 替代方案：沿用 tick-driven 慣例，把翻格判定也塞進 16ms 的 `step()`——放棄，翻格是離散事件，用連續 tick 檢查沒有任何好處，只是徒增複雜度。

3. **首格必安全：地雷佈局延後到第一次翻格才生成，排除該格與其 8 個鄰居**
   - 理由：這是全球踩地雷實作的標準慣例（Windows 踩地雷、多數線上版本皆如此），避免玩家開局第一下就踩雷、毫無策略可言的挫折體驗；同時保證開局有一定機率出現連鎖展開的空曠區域，符合玩家對這個 genre 的既有預期。
   - 做法：`MinesweeperEngine.reset(levelConfig)` 只建立空白棋盤（不放地雷）；`reveal()` 偵測到「這是本關第一次呼叫」時，才依地雷數在扣除「第一格＋其 8 個鄰居」後的候選格中隨機佈雷，接著才執行正常的翻格與連鎖展開流程。

4. **計分公式：每關「基礎分 - 花費秒數 × 每秒扣分」，下限為保底分；總分＝已過關卡加總**
   - 理由：使用者明確要求「計時制，時間越短分數越高」；用簡單的線性遞減公式（比照 tetriminos／match3 的既有「公式直觀好懂」風格），每關訂一個基礎分（難度越高基礎分越高，符合「比較難的關卡本來就該多給分」的直覺）與保底分（避免算出負分或 0 分讓玩家覺得白玩）。
   - 五關數值（基礎分／每秒扣分／保底分，隨難度遞增）：
     | 關卡 | 棋盤 | 地雷數 | 密度 | 基礎分 | 每秒扣分 | 保底分 |
     |---|---|---|---|---|---|---|
     | 1 | 8×8 | 6 | 9.4% | 100 | 2 | 20 |
     | 2 | 9×9 | 10 | 12.3% | 150 | 2 | 30 |
     | 3 | 10×10 | 16 | 16.0% | 220 | 2 | 50 |
     | 4 | 11×11 | 22 | 18.2% | 300 | 3 | 60 |
     | 5 | 12×12 | 30 | 20.8% | 400 | 3 | 80 |
   - 理論總分上限（5 關皆瞬間過關，僅為數學上限，非實際可達）＝ 100+150+220+300+400 ＝ 1170；這也是本次計分模型「有明確理論上限」的具體數字依據（對照 Decision 6 的 `maxReasonableScore`）。
   - **地雷數 v2 調整（實作上線後校準）**：初版地雷數（10/13/18/24/30）換算密度是 15.6%→16.0%→18.0%→19.8%→20.8%，Lv1 就已經落在 Windows 踩地雷「中級」密度區間（15.6%），對第一關來說不夠簡單；改為 6/10/16/22/30，密度 9.4%→12.3%→16.0%→18.2%→20.8%，對齊 Windows 踩地雷的初級／中級／高級三個經典難度基準點（Lv2≈初級 12.3%、Lv3≈中級 16%、Lv5≈高級 20.6%），Lv1 明顯低於初級、真正簡單；五關之間的密度級距也更平滑（+2.9/+3.7/+2.2/+2.6 個百分點，原本是 +0.4/+2.0/+1.8/+1.0，前段幾乎沒級距、後段落差偏大）。棋盤尺寸與計分公式（基礎分／每秒扣分／保底分／理論上限 1170）皆不變，只調地雷數本身。
   - 替代方案：比例制（`基礎分 × 目標時間 ÷ 實際花費時間`）——放棄，線性遞減公式更直觀、更容易在 RULE 說明裡講清楚，且不會因為「花費時間趨近 0」而產生失控的高倍率分數。

5. **地雷密度隨關卡遞增（約 15.6% → 20.8%），棋盤格子固定像素大小，關卡越高棋盤越大**
   - 理由：地雷密度遞增＋棋盤變大是踩地雷「難度曲線」的標準做法（對照 Windows 踩地雷的初級/中級/高級三檔預設），5 關取其間插值出更平滑的遞增曲線；固定格子像素大小（不隨關卡縮放）讓後面關卡的棋盤在視覺上明顯「變大」，直覺傳達難度提升。
   - 做法：`CELL_SIZE` 固定（例如 32px），各關棋盤總寬高 ＝ `CELL_SIZE × 關卡邊長`（256px～384px），比照其他遊戲頁面「`.frame` 用 `fit-content` 包住內容、`.stage` 用 `box-sizing: content-box`」的既有版面手法（見 PONG／RUNNER／SPACE SHOOTER 修過的尺寸錯位教訓），避免同樣的版面錯位問題在不同關卡的棋盤尺寸切換時重演。

6. **Coin 倍率獨立估算，`maxReasonableScore` 直接對齊 Decision 4 算出的理論上限（1170），不像其他遊戲需要抓寬裕估計值**
   - 理由：MINESWEEPER 是本次唯一「有精確數學上限」的計分模型（5 關基礎分固定加總），不像其他遊戲的分數開放式成長、只能抓寬裕估計值；因此 `maxReasonableScore()` 可以设得比其他遊戲更貼近真實上限，防偽造的意義更純粹（任何超過 1170 的回報值都是確定的異常，不是「玩很久也有可能達到」的模糊地帶）。
   - 初始估算：一場中等發揮（多數關卡不是最快但也沒拖太久）預期總分落在 400–700 區間；抓 `coinRate: 0.2`（550 分 ≈ 110 coin，對齊既有「一場優秀表現 ≈ 100 coin」的既有目標）、`coinCapPerRun: 300`（沿用多數遊戲的既有慣例，本來就略高於理論上限 1170 × 0.2 ＝ 234，幾乎不會真的觸頂，純粹防呆）、`coinDailyCap: 100000`（沿用既有慣例）。`maxReasonableScore()` 設為 `1200`（略高於精確上限 1170，抓一點點餘裕即可，不需要像開放式計分遊戲那樣抓到好幾倍）。
   - 這些是程式碼估算值，比照既有慣例，上線後應實測校準。

7. **操作方式：左鍵／點擊翻格，右鍵插旗；另提供「插旗模式」切換鈕，供無法右鍵的觸控裝置使用**
   - 理由：右鍵插旗是踩地雷的標準操作，但觸控裝置沒有右鍵，若只支援右鍵會讓手機/平板玩家完全無法插旗；提供一顆「🚩 插旗模式」切換鈕，開啟後點擊格子變成插旗而非翻格，是業界常見的觸控替代方案。
   - 做法：格子的 `contextmenu` 事件呼叫 `event.preventDefault()` 並執行插旗（阻止瀏覽器原生右鍵選單彈出）；插旗模式開關是頁面層級的 UI 狀態（不影響 `MinesweeperEngine` 本身），開啟時一般點擊呼叫 `toggleFlag()` 而非 `reveal()`。

8. **Server／API／client 資料層完全比照既有慣例擴充，不做任何架構調整**
   - `RETRO_GAME_BASE` 不變、`server/api/games/retro/<game>/history.*` 資料夾樣式不變、`app/services/api.ts` 的 `api.games.retro.*` 命名方式不變、`useGameHistory.ts` 的 `GAME_KEYS`／`_handlers.gameApi()` switch 擴充一個分支即可，`server/middleware/auth.ts` 的 `/api/games` 前綴保護與 `BalanceChangeType` 的 `'game-reward'` 皆已涵蓋，不需修改。
   - `useGameHistory` 的 `level` 欄位借用來記錄「這場結束在第幾關（或全部通關）」，比照其他遊戲把 `level` 當作進度指標的既有用法，不是全新語意。

## Risks / Trade-offs

- [風險] 首度引入關卡制，若未來又新增第二款「多關卡」遊戲，需要重新評估是否該抽出共用的「關卡進度」邏輯（目前只有這一款，先不預先設計成通用機制，避免過度設計／YAGNI）。
- [風險] 線性遞減計分公式如果「每秒扣分」抓太重，玩家稍微猶豫一下分數就快速趨近保底分，體感不佳——因應：`每秒扣分`／`保底分` 皆為獨立常數，上線後可依實測調整，不影響架構。
- [風險] 地雷密度／棋盤大小是依 Windows 踩地雷既有難度預設插值估算，5 關之間的難度落差可能不夠平滑（例如第 4 關明顯比第 3 關難很多）——因應：`LEVELS` 是一個常數陣列，上線後可個別調整任一關卡的數值，不影響其他關卡與架構本身。
- [風險] 觸控裝置的「插旗模式」切換鈕如果玩家沒注意到，可能會覺得「無法插旗」——因應：WELCOME／RULE 說明會明確提及切換鈕的存在與操作方式。

## Migration Plan

- 全新功能，無既有資料需要遷移，且刻意設計成獨立的 `gameKey`，不影響既有八款遊戲的紀錄與 coin 上限。
- 部署順序（每一步都可獨立回滾，比照既有幾次擴充的分步策略）：
  1. Server 端服務層與 `storage.ts` 註冊（尚未被路由引用，無風險）
  2. Server 端 API 路由（存在但尚未被前端呼叫，無風險）
  3. Client `app/services/api.ts` 擴充
  4. `useGameHistory.ts` 擴充
  5. 遊戲頁面 `app/pages/game/minesweeper.vue`（此步驟起才有實際資料寫入行為）
  6. `game-hall.vue` + `GameMachineCard.vue` + `GameHistoryDialog.vue`（此步驟起使用者才看得到入口，是唯一改變可見行為的步驟）

## Open Questions

- 每關的「基礎分／每秒扣分／保底分」與地雷密度都是拍腦袋估算，上線後建議實際玩過 5 關記錄花費時間分佈再校準（比照既有遊戲常數的 Follow-up 慣例）。
- 是否需要在 HUD 顯示「目前關卡剩餘地雷數（總地雷數－已插旗數）」這個經典踩地雷 UI 元素？屬於實作細節，留待實作階段決定，不影響本次架構規劃。
- 是否要對「踩到雷」提供一次「查看完整地雷位置」的結算畫面（比照 Windows 踩地雷輸掉時攤開全部地雷）？屬於呈現細節，不影響架構，留待實作時一併決定。
