## Context

`Match3CoreEngine`（`app/utils/match3Engine.ts`）原本只做最基本的三消：交換→偵測任意方向 3 連消以上→清除→掉落補位→再偵測，計分是 `matchedCount × 4 × (1 + (round-1) × 0.5)`。使用者提供完整的三消規則文件，要求補上特殊方塊與全新 Combo 計分模型。本次規劃先請一個 Plan agent 對第一版設計做邊界情況壓力測試，抓出幾個真正的漏洞（雙特殊方塊互換未定義、無解偵測跟「交換特殊方塊必定合法」互相打架、洗牌可能默默吃掉玩家的特殊方塊、Combo×爆炸清除格數是複合成長不是單純線性），本文件記錄修正後、也是實際實作採用的版本。

## Goals / Non-Goals

**Goals:**
- 4 連消→Line Bomb（清整排/整列）、5 連消以上→Color Bomb（清全場同色）、L/T 型連消→Bomb（清 3×3）。
- 特殊方塊三種觸發方式：被直接消除、被爆炸波及、被玩家直接交換（永遠合法、不復位）。
- Combo 計分模型：每次玩家操作 Combo 從 ×1 起算，每多一輪連鎖 +1，分數＝清除格數 × 每格基礎分 × Combo，連鎖結束歸零。

**Non-Goals:**
- Color Bomb 與其他特殊方塊組合出「新效果」（例如「全場同色變 Line Bomb」）——規則文件明確列為「後續版本」；雙特殊方塊互換時兩者仍各自獨立引爆，只是不做組合出新效果的邏輯。
- 粒子特效系統（只做簡單 CSS 動畫，比照專案「不用 canvas」的既有慣例）。

## Decisions

1. **資料模型：保留 `grid: number[][]`（顏色），另加一層平行的 `special: Match3SpecialKind[][]`**
   - 理由：第一版設計打算把 `grid` 改成 `{ color, special }[][]` 物件，會動到既有引擎裡每一處 `grid[r][c] === ...` 的顏色比對邏輯，churn 大又容易漏改。改成「顏色陣列不變、另外疊一層平行陣列」風險小很多，既有的 `hasAnyValidMove()`／run-scanning 顏色比對完全不用碰。Color Bomb 沒有固定顏色，`grid` 上的值沿用它被創造那一格原本的顏色，純粹當歷史殘留值。

2. **消除偵測：`findMatchGroups()` 回傳帶形狀資訊的群組，特殊方塊格永遠不參與被動連線偵測**
   - 掃橫向／縱向連續同色 run（≥3）時，任何 `special[r][c] !== 'none'` 的格子直接排除在外（不參與、不延伸、不形成任何 run）——避免特殊方塊格用「湊三連」的方式意外自己生成新效果。
   - 長度恰好 3 → `line3`（無特殊方塊）；恰好 4 → `line4`（產生對應方向的 Line Bomb）；≥5 → `line5plus`（產生 Color Bomb）。
   - 一個橫向 3-run 與一個縱向 3-run 恰好共用一格 → 合併成 `corner` 群組（產生 Bomb，位置在共用格）；長度 ≥4 的 run 不參與 corner 合併（4/5 連消優先於 L/T）。

3. **特殊方塊生成位置**
   - 玩家交換觸發：生成在 `to` 格（`to` 不在群組內才退而求其次用 `from`）。一次交換可能同時產生兩個群組（`from` 一個、`to` 一個）——兩個群組各自獨立生成各自的特殊方塊；`from`／`to` 同時落在同一群組——只生成一個在 `to`。
   - 連鎖（非玩家直接交換）觸發：生成在該 run 的幾何中點格（`corner` 群組生成在交叉格）。
   - 新生成的特殊方塊在生成當下這一輪對任何爆炸波及免疫。

4. **引爆／連鎖清除：worklist 處理，Line Bomb／Bomb 優先於 Color Bomb**
   - 每輪：清除集合初始化為所有群組 cells 的聯集；worklist 依序處理清除集合中的特殊方塊，把爆炸範圍併入清除集合，直到沒有新的特殊方塊被捲入；用「已處理位置」集合保證終止。
   - 同一輪內若同時有多顆待處理的特殊方塊，Line Bomb／Bomb 先處理，Color Bomb 最後處理（讓它判斷目標色時能看到最完整的清除集合，結果才是確定性的），同優先權依左上到右下排序。

5. **Color Bomb 目標色判定**
   - 玩家直接交換觸發、對方是普通色：目標色＝該普通方塊的顏色。
   - 玩家直接交換觸發、對方也是 Color Bomb：退回「全盤面出現次數最多的顏色」。
   - 連鎖中被波及觸發：目標色＝當下清除集合中其他普通色格的眾數；沒有普通色格則退回全盤面眾數；仍打平取顏色編號最小的（確定性 tie-break）。

6. **玩家直接交換特殊方塊：永遠合法、必定觸發；雙特殊方塊互換的行為明確定義**
   - 恰好一邊是特殊方塊：交換直接視為合法，該特殊方塊立即引爆，Combo 從 ×1 起算。
   - 兩邊都是特殊方塊：兩顆都視為合法交換並各自獨立引爆，不額外產生組合技加成效果（規則文件明確列為後續版本）。

7. **Combo 計分模型，含封頂機制**
   - 本輪分數＝清除格數 × 4（每格基礎分） × `min(Combo, COMBO_CAP)`；`COMBO_CAP = 6`。
   - 另加 `ROUND_SCORE_CAP = 500`（單輪分數上限）與 `CHAIN_SCORE_CAP = 2000`（整條連鎖總分上限），回應「特殊方塊清除格數變多」與「Combo 線性成長」是相乘而非相加關係的複合成長風險——這是設計本身的一部分，不是留到事後才調。
   - 即使加了封頂，一般情況分數量級仍會比原本公式高，`coinRate`（0.25）／`maxReasonableScore`（RUSH 8000／CLASSIC 3200）／Lv 門檻（`[0,80,200,400,800]`）預期需要在實測後重新校準，列入 Follow-up。

8. **無解偵測與洗牌需要跟「交換特殊方塊必定合法」協調**
   - `hasAnyValidMove()` 維持只檢查顏色連消是否存在，刻意不把「交換特殊方塊永遠合法」算進「有沒有解」——洗牌是為了保證還有新的顏色消除可湊，不是為了保證玩家永遠有事可做（後者本來就有特殊方塊可以交換）。
   - 洗牌時只重新隨機化 `special === 'none'` 的普通格，既有特殊方塊原地保留（顏色與種類都不動），避免玩家辛苦湊出來的特殊方塊被無聲吃掉。

9. **Classic 限步數的扣步判定明確涵蓋特殊方塊觸發**
   - 只要有交換行為造成至少一格被清除，`matched` 就是 `true`、扣一步；兩邊都是普通色且交換後沒有任何消除，才是唯一的「不扣步」情況（跟既有行為一致）。

10. **UI 呈現**
    - 棋盤格特殊方塊疊加圖示：Line Bomb 用 ↔️（清整排）/↕️（清整列）、Bomb 用 💣、Color Bomb 用 🌈。
    - Combo 彈出文字從 Combo ×1 就顯示，字體大小隨 Combo 數值放大（`clamp` 概念，JS 端計算 `Math.min(0.9 + combo * 0.15, 2.5)rem`）。

## Risks / Trade-offs

- [風險] 計分／coin 經濟需要後續調校——即使加了封頂機制，仍預期需要在實測後重新校準 `coinRate`／`maxReasonableScore`／Lv 門檻，不阻擋本次設計，列入驗證清單。
- [風險] `COMBO_CAP`／`ROUND_SCORE_CAP`／`CHAIN_SCORE_CAP` 是估計值，上線後可依實測分數分佈調整。
- [風險] `findMatchGroups()` 的 L/T 合併邏輯只處理「恰好 3」的 run 兩兩配對，若同一個 3-run 理論上可能同時跟多個垂直 3-run 相交（例如十字形），目前實作只會取第一個配對成功的組合（`consumedH`/`consumedV` 一次性標記），屬於刻意簡化，未特別針對這種罕見情況設計。

## Migration Plan

- 全新機制，無既有資料需要遷移；不影響既有的遊戲紀錄資料結構與 coin 兌換流程。
- 已完成實作與驗證：用 Playwright 隨機操作近 1200 次交換，確認 4 種特殊方塊（💣／🌈／↔️／↕️）皆能自然生成、直接交換特殊方塊會觸發（分數正確變化）、Combo 彈出與縮放正常、過程中無 console 錯誤與卡死。

## Follow-up

- 實際玩測幾局記錄分數分佈，評估是否需要重新校準 `coinRate`／`maxReasonableScore`／Lv 門檻（見 Decision 7）。
