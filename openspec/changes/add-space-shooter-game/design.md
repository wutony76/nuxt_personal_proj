## Context

- `add-game-history` 已建立 game-hall 小遊戲的完整架構：client 頁面自包含（engine class + reactive 鏡像 snapshot）＋ `useGameHistory`（A/B 雙模式）＋ server 端 `RETRO_GAME_BASE`（共用基底＋每款遊戲一個服務檔＋每款遊戲一組 API 路由資料夾）。
- 現有七款遊戲裡，除 PONG（多局賽制、勝場數計分）外，其餘六款都是「單命、撞到／失敗即結束」的連續衝分玩法。SPACE SHOOTER 是本次唯一要引入「生命值（多條命）」機制的遊戲——玩家被擊中不會立即結束，而是扣一條命、短暫無敵後重生，命數歸零才真正結束。這是本次架構上第二個特例（第一個特例是 PONG 的多局賽制），需要在 design 中明確記錄取捨理由，避免跟既有慣例混淆。
- 現有遊戲的碰撞系統都是「單一物件 vs 單一角色」（snake 撞自己、racing 撞牆、runner 撞障礙、pong 球拍撞球）；SPACE SHOOTER 首次需要「雙向拋射物」碰撞：玩家子彈打敵機、敵彈打玩家，兩組獨立的碰撞判定同時存在，架構複雜度略高於前六款，但仍在既有「頁面自包含 engine class + tick 驅動」的框架內，不需要新的架構模式。
- `racing.ts`／`runner.ts`（開放式存活計分）與 `tetriminos.ts`（`cleared*100+(cleared-1)*50` 累加型計分）是最接近的兩種既有計分哲學；SPACE SHOOTER 的「擊落敵機得分」屬於累加型（比較接近 tetriminos／match3 的「事件觸發加分」模式），跟 racing／runner 的「隨時間累加」不同，因此 coin 倍率不能直接沿用 racing／runner，需要獨立估算（比照 match3 當初的做法）。

## Goals / Non-Goals

**Goals:**
- 提供一款經典俯視角射擊玩法：玩家左右移動＋連續射擊＋閃避敵機與敵彈，分兩種敵機提供分數與難度層次。
- 首次導入「生命值」機制，讓射擊類型有更貼近 genre 慣例的容錯度（不是碰一下就結束），同時把這個特例明確記錄在架構文件中。
- 補上「連擊倍率」「道具掉落」「里程碑強敵」「視覺特效」四項豐富度，讓核心的「移動＋射擊＋閃避」在重複多次後仍有變化與正向回饋，而不是單調的無腦掃射。
- Server 端、client 資料層、game-hall 入口完全比照既有七款遊戲的慣例逐一擴充，不引入新的資料庫或跨遊戲共用邏輯。

**Non-Goals:**
- 不做關卡／過關解鎖制（沒有「破關進下一關」的目標，維持跟 RUNNER／racing 一樣的「連續生存＋分數持續累加」模式，只是用「生命值」取代「單次失誤即死」）。
- 不做完整 boss 戰系統（無過關／波次狀態機、無多階段攻擊型態）——但會有「里程碑強敵」這種輕量替代做法（見 Decision 9），純粹是「分數達門檻多生成一隻特殊敵機」，不是真正的 boss 關卡。
- 不做武器「永久」升級（道具強化是限時效果，見 Decision 7；沒有「打死怪掉裝備、永久改變武器基礎能力」的養成系統）。
- 不做多人合作／對戰。
- 不引入資料庫；server 端持久化沿用專案現況的 in-memory 作法。
- 不做遊戲重播、不儲存完整過程，只存結算後的摘要（分數、等級）。

## Decisions

1. **首度引入生命值機制（3 條命），而非沿用「碰一下即結束」的既有慣例**
   - 理由：橫向捲軸／俯視角射擊遊戲的玩家同時要處理移動、瞄準、閃避三件事，資訊密度明顯高於前六款遊戲（尤其同時有敵機本體與敵彈兩種威脅），若沿用單命制，玩家會覺得懲罰過重、無法累積有意義的分數；多命制也是這個 genre（Galaga、1943、東方系列）幾乎全部採用的標準做法，符合玩家對「太空射擊」的既有預期。
   - 取捨：這是本次架構第二個特例（第一個是 PONG 的多局賽制），`useGameHistory` 的 `score` 依然只記錄最終分數，生命值本身是純前端遊戲內狀態、不落地紀錄，不影響資料層設計；被擊中後給 1.5 秒無敵時間＋重生於畫面下方中央，避免「一次判定就連續扣好幾命」的連鎖懲罰。
   - 替代方案：沿用單命制——放棄，不符合射擊類型的玩家預期，且會讓「敵彈閃避」這個核心互動變得過於懲罰性。

2. **敵機持續生成（無離散波次），比照 runner 既有的連續生成模式，而非「一波清完才生下一波」的傳統作法**
   - 理由：離散波次（清完一波才出下一波）需要額外的「波次狀態機」與「波次間過場」設計，屬於不同規模的功能；沿用 RUNNER／racing 已經驗證過的「持續生成＋難度隨分數/等級提升」模式，架構上完全一致，也讓「連續衝分」的核心玩法感受跟現有遊戲保持一致。
   - 替代方案：離散波次制（比照 Galaga 原版）——放棄，增加不必要的狀態複雜度，且與本次 Non-Goals（不做過關制）衝突。

3. **敵機分兩型：基本（低血量／低分／不開火）、強化（高血量／高分／不定期向下開火）**
   - 理由：只有一種敵機會讓遊戲缺乏層次；兩型已經足夠讓「基本敵機用來衝分、強化敵機提供風險與威脅」的核心張力成立，避免一開始就做三種以上敵機增加不必要的美術/平衡工作量。
   - 做法：基本敵機 1 點血量、擊落得 10 分；強化敵機 3 點血量、擊落得 40 分，且每隔一段時間會向下發射一顆敵彈。兩者的生成比例隨等級提升（等級越高，強化敵機比例越高）。

4. **雙向拋射物碰撞：玩家子彈（往上飛）vs 敵機／敵彈（往下飛）vs 玩家本體，各自獨立判定**
   - 理由：這是本次唯一需要處理「兩組獨立飛行物」碰撞的遊戲（前六款都只有單一方向的威脅）；比照既有「用固定 x/y 範圍矩形相交」的判定手法（見 pong.vue／runner.vue 既有做法）分別套用在「玩家子彈 vs 敵機」與「敵彈／敵機本體 vs 玩家」兩組獨立檢查上，不需要引入新的碰撞演算法，只是檢查的物件組合變多。
   - 做法：`step()` 內依序處理（1）子彈與敵機位置更新、（2）子彈-敵機碰撞（命中則敵機扣血、血量歸零則移除並加分）、（3）敵彈與敵機本體位置更新、（4）敵彈／敵機本體與玩家碰撞（若玩家不在無敵狀態則扣命）。

5. **分數計分模型比照 tetriminos／match3 的「事件觸發加分」，coin 倍率獨立估算，不沿用 racing/runner 的開放式存活倍率**
   - 理由：SPACE SHOOTER 的分數是「擊落敵機」離散事件的加總，跟 racing／runner「持續存活時間」的計分哲學不同，數值成長曲線也不同（前者跟"擊殺效率"相關，後者純粹跟時間相關），直接沿用 racing 的 `coinRate: 0.5` 會因為分數量級不同而失衡。
   - 初始估算：基本敵機 10 分／強化敵機 40 分／里程碑強敵 150 分，且會被連擊倍率（見 Decision 8，最高 x4）放大，搭配 3 條命與道具強化（見 Decision 7）帶來的容錯，一場中高水準的對局預期總分落在 1000–3000 區間；抓 `coinRate: 0.08`（1250 分 ≈ 100 coin，對齊既有「一場優秀表現 ≈ 100 coin」的既有目標）、`coinDailyCap: 100000`（沿用既有慣例）。
   - **`coinCapPerRun` 使用者明確要求提高到 `2500`**（其他七款遊戲皆為 `300`），也就是接受「分數本身可以衝很高沒關係」，單局最多能拿到的 coin 明顯高於其他遊戲——這是刻意的差異化決策，不是估算疏忽。`maxReasonableScore()`（防偽造上限，非設計天花板）需相應提高到 `40000`：因為要讓 `coinCapPerRun: 2500` 真的可以被打到（`2500 ÷ 0.08 = 31250` 分才能觸頂），若沿用原本較低的估計值，反而會讓玩家分數還沒衝到能拿滿 2500 coin 就先被防偽造上限攔下來，變相削弱這次使用者想要的效果。
   - 這些是程式碼估算值，比照既有慣例，上線後應實測校準；`coinCapPerRun: 2500` 是本次唯一明顯偏離「其他遊戲都是 300」既有慣例的地方，屬於使用者對這款遊戲的刻意差異化，不需要往回校正成跟其他遊戲一致。

6. **Server／API／client 資料層完全比照既有慣例擴充，不做任何架構調整**
   - `RETRO_GAME_BASE` 不變、`server/api/games/retro/<game>/history.*` 資料夾樣式不變、`app/services/api.ts` 的 `api.games.retro.*` 命名方式不變、`useGameHistory.ts` 的 `GAME_KEYS`／`_handlers.gameApi()` switch 擴充一個分支即可，`server/middleware/auth.ts` 的 `/api/games` 前綴保護與 `BalanceChangeType` 的 `'game-reward'` 皆已涵蓋，不需修改。
   - `gameKey` 採用 `'spaceShooter'`（camelCase，比照 `match3rush`／`match3classic` 的既有多字複合 key 命名慣例），路由路徑採 `space-shooter`（kebab-case，比照既有路由資料夾的命名風格，兩者不需要字面一致，如同 `match3rush` 的路由資料夾其實是 `match3rush` 而非 `match3-rush`——這裡刻意選 kebab-case 路由是因為"Space Shooter" 是兩個英文單字組成，kebab-case 路由可讀性較好，不影響前後端介面設計）。

7. **道具掉落：護盾／加速射擊／散射彈，機率掉落、飛過即拾取，武器類強化限時、護盾為一次性**
   - 理由：使用者明確要求補上道具豐富度；護盾／加速射擊／散射彈是這個 genre 最經典的三種強化，能立即提升「打得更爽」與「容錯更高」兩種體驗，且不需要引入裝備欄位或永久養成系統，維持單局內效果、局外不留存的既有精神（跟其他遊戲一樣「這局的狀態不影響下一局」）。
   - 做法：敵機被擊落時有機率掉落一個道具物件（基本敵機掉落機率較低、強化敵機與里程碑強敵較高，見 Decision 3／9），道具緩慢下落，玩家飛船碰到即拾取，不需要額外按鍵。「加速射擊」與「散射彈」是同一個「武器強化」欄位（拾取新的會覆蓋舊的、重新計時，不疊加），限時（例如 8 秒）；「護盾」是獨立的一次性標記，拾取後在下次被擊中時抵銷傷害並消耗掉，兩者可以同時持有（武器強化 + 護盾互不影響）。
   - 替代方案：做成永久性武器升級（打死敵機換裝備、越打越強）——放棄，這需要跨局的裝備狀態管理，跟現有「每局重新開始、乾淨的初始狀態」慣例衝突，且大幅超出這次要豐富的範疇。

8. **連擊／分數倍率：連續擊殺不中斷即提升倍率，被擊中歸零**
   - 理由：使用者明確要求；這是零架構成本、純粹分數計算層面的豐富化——不需要新的實體或碰撞判定，只需要一個 `comboCount` 計數器與對應的倍率查表，就能讓玩家在「要不要冒險貼身多打幾隻」與「保守閃避保住連擊」之間做出選擇，是射擊遊戲很經典的風險/回饋機制。
   - 做法：`comboCount` 每次擊落敵機（含里程碑強敵）+1，倍率依門檻分級：0–4 下 x1、5–11 下 x2、12–23 下 x3、24 下以上 x4；玩家被擊中扣命的瞬間 `comboCount` 歸零、倍率回到 x1。每次擊殺加分 ＝ 該敵機基礎分數 × 當下倍率。
   - 替代方案：倍率隨「時間」而非「連續擊殺」遞增（例如存活越久倍率越高）——放棄，那樣倍率會跟「擊殺」這個核心動作脫鉤，變成只要活著不動也能漲倍率，失去風險/回饋的設計意圖。

9. **里程碑強敵：分數每跨過固定門檻，額外生成一隻高血量／高分／橫掃移動的獨特敵機，不是完整 boss 系統**
   - 理由：使用者明確要求「不是完整 boss 系統」的輕量版本；沿用 Decision 2 的「持續生成、無波次狀態機」既有做法，只是額外多生成一隻特殊個體，不需要引入任何「進入 boss 戰／關卡鎖定／多階段攻擊」的新狀態機，維持架構複雜度最低。
   - 做法：每當分數跨過門檻（每 200 分一次，見 Decision 11 調降後的數值），额外生成一隻「里程碑強敵」：血量遠高於強化敵機（例如 10 點）、分數大幅提高（見 Decision 11，仍會被連擊倍率放大）、移動方式改為左右橫掃全螢幕寬度（而非單純下降＋正弦漂移），視覺尺寸較大；擊落必定掉落一個道具（見 Decision 7），作為玩家通過這個節奏亮點的獎勵。與一般敵機一樣使用「玩家子彈 vs 敵機」的既有碰撞判定，不需要新的判定邏輯。
   - 替代方案：完整 boss 戰（血條 UI、多階段攻擊、專屬過場）——放棄，這需要關卡/波次狀態機與大量客製攻擊模式，跟 Non-Goals 明確排除的範疇衝突。

10. **視覺特效加強：星空視差背景／爆炸粒子／受擊震動，純呈現層，不影響任何遊戲邏輯**
    - 理由：使用者明確要求；這三項全部是「讀取既有狀態、疊加視覺效果」的呈現層工作，不需要新增任何碰撞判定或資料欄位，是投入產出比最高的豐富化方向。
    - 做法：
      - 星空視差背景：初始化時生成固定數量的星點（不同大小＝不同層），`step()` 內依所屬層的速度往下移動、超出畫面下緣即回收到頂部重新出現（比照既有障礙物回收邏輯的手法，套用在裝飾性物件上）。
      - 爆炸粒子：敵機／玩家被擊中時，於命中位置插入一個短生命週期的爆炸動畫元素（比照 pong.vue 的 `serve-flash` 與 match3-rush 的 `combo-popup` 既有做法：一次性 CSS 動畫，動畫結束後自動從陣列移除，不用計時器手動清除也可以直接用 `animationend` 事件）。
      - 受擊震動：玩家被擊中扣命時，對 `.ss-stage` 短暫套用一個 shake 動畫 class（比照 snake.vue 既有的 `stage-shake` 手法）。
    - 這些效果全部只讀取既有的遊戲狀態（敵機死亡、玩家受擊等事件），不會反過來影響任何判定或分數計算，因此不需要新增 `openspec` 的行為規格（ADDED Requirement）——純視覺呈現不屬於這份文件要規範的「行為」範疇。

11. **上線後試玩發現 SCORE 數字量級偏高，調降計分公式並同步校準 coinRate／等級門檻／里程碑門檻／maxReasonableScore**
    - 理由：使用者實際試玩後回報分數偏高（比照 `add-match3-games` Decision 8 當時遇到的同類問題），問題出在畫面上的分數本身量級，不是 coin 兌換比例，因此調整計分公式而非只調 coinRate。
    - 做法：`ENEMY_STATS` 的敵機基礎分數整體調降至約原本的 0.4 倍（基本敵機 10→4 分、強化敵機 40→15 分）、`MILESTONE_STATS.score` 調降（150→50 分）；連鎖調整 `MILESTONE_SCORE_STEP`（500→200）與 `LEVEL_SCORE_THRESHOLDS`（`[0,300,700,1400,2500]`→`[0,120,280,560,1000]`），維持原本「多久見到一次里程碑強敵／多久升一次 Lv」的節奏不變。
    - 連動調整（維持「一場優秀表現 ≈ 100 coin」的既有目標，見 Decision 5）：`coinRate` 由 `0.08` 反向調高為 `0.2`（分數降為約 0.4 倍，倍率對應調高為約 2.5 倍，兩者相乘後單位分數換算的 coin 量級大致不變）；`maxReasonableScore()` 等比例調降（`40000`→`16000`，仍需高於 `coinCapPerRun ÷ coinRate = 2500 ÷ 0.2 = 12500`，確保使用者明確要求的 `coinCapPerRun: 2500` 仍然可以被打到，不會被防偽造上限反過來卡住）。`coinCapPerRun: 2500` 本身維持不變（那是獨立於分數量級的刻意決策，見 Decision 5）。
    - 這些仍是估算值，如同 Decision 5，屬於「先讓機制跑起來，之後可依實測數據再校準」的常數，不影響架構本身。

12. **使用者再次指定分數比例改為 1:3:5（基本 1／強化 3／里程碑 5），比 Decision 11 的估算再大幅調降**
    - 理由：Decision 11 的調降幅度（0.4 倍）試玩後仍嫌偏高，使用者直接指定明確的相對比例（1:3:5），不再是「等比例縮放舊數值」而是全新指定的絕對值，因此改用「依擊殺數反推分數門檻」而非線性縮放舊門檻，避免縮放誤差累積。
    - 做法：`ENEMY_STATS.basic.score: 4→1`、`ENEMY_STATS.tough.score: 15→3`、`MILESTONE_STATS.score: 50→5`。以「維持原始（Decision 11 之前）設計時，各等級所需擊殺數」為基準反推新門檻：依目前 `TOUGH_CHANCE_BASE`／`TOUGH_CHANCE_PER_LEVEL` 換算各等級平均每次擊殺分數（約 1.4～2.0 分／殺，隨等級提升強化敵機比例增加而略增），反推 `LEVEL_SCORE_THRESHOLDS: [0,120,280,560,1000]→[0,25,60,120,200]`、`MILESTONE_SCORE_STEP: 200→50`，讓玩家仍需要跟原本差不多的擊殺數量才能升級／見到里程碑強敵，而不是被新的極小分數值害得「升級速度暴增」或「幾乎不會升級」。
    - 連動調整（維持「一場優秀表現 ≈ 100 coin」的既有目標）：`coinRate` 由 `0.2` 再調高為 `0.3`；`maxReasonableScore()` 由 `16000` 調降為 `10000`（仍需高於 `coinCapPerRun ÷ coinRate = 2500 ÷ 0.3 ≈ 8334`，確保 `coinCapPerRun: 2500` 依然可達成）。
    - 這些同樣是估算值，上線後應以實測的「擊殺數 vs 升級節奏」手感為準再校準，不影響架構本身。

## Risks / Trade-offs

- [風險] 生命值機制是本次唯一的特例，若未來又新增第三款「多命制」遊戲，需要重新評估這是否該變成新的既有慣例（目前只有這一款，先不預先設計成通用機制，避免過度設計／YAGNI）。
- [風險] 敵彈與敵機本體同時判定可能造成「明明看起來閃過了還是扣命」的誤判——因應：玩家碰撞箱刻意抓得比視覺圖形略小（比照 runner 既有的寬容判定慣例），且擊中後有無敵時間與短暫視覺提示，降低誤判帶來的挫折感。
- [風險] coin 倍率是根據「預期擊殺數＋連擊倍率」的推測值，非實測數據，可能出現「比其他遊戲好賺／難賺」的落差——因應：`coinRate`／`maxReasonableScore` 是獨立於 `spaceShooter.ts` 的常數，上線後可單獨調整，不影響其他遊戲。
- [風險] 敵機生成頻率、敵彈頻率、玩家/敵方子彈速度皆為拍腦袋估算，可能太難（3 條命很快耗盡）或太簡單（幾乎不會扣命）——因應：比照既有遊戲做法，先讓機制跑起來，上線後依實測調整常數，不影響架構本身。
- [風險] 道具掉落機率、連擊倍率門檻、里程碑強敵的門檻與數值都是新增的估算值，彼此會互相放大（連擊 x4 + 加速射擊/散射彈同時生效時，短時間內分數增速可能遠高於預期）——因應：這幾個常數彼此獨立（掉落機率／倍率門檻／里程碑門檻／強敵數值都各自是獨立常數），上線後可以分別微調，不需要重新設計架構；`coinCapPerRun`（單局上限）本來就是為了夾住這類極端情況而存在的既有機制。
- [風險] 視覺特效（粒子、星空、震動）如果同時大量觸發（例如密集連續擊殺）可能造成效能疑慮——因應：粒子與星空數量抓固定上限（例如同時最多 N 個粒子、固定星點數），且都是輕量 CSS transform 動畫（非 canvas 逐幀運算），比照現有遊戲的 CSS 動畫慣例，效能疑慮低。

## Migration Plan

- 全新功能，無既有資料需要遷移，且刻意設計成獨立的 `gameKey`，不影響既有七款遊戲的紀錄與 coin 上限。
- 部署順序（每一步都可獨立回滾，比照既有幾次擴充的分步策略）：
  1. Server 端服務層與 `storage.ts` 註冊（尚未被路由引用，無風險）
  2. Server 端 API 路由（存在但尚未被前端呼叫，無風險）
  3. Client `app/services/api.ts` 擴充
  4. `useGameHistory.ts` 擴充
  5. 遊戲頁面 `app/pages/game/space-shooter.vue`（此步驟起才有實際資料寫入行為）
  6. `game-hall.vue` + `GameMachineCard.vue` + `GameHistoryDialog.vue`（此步驟起使用者才看得到入口，是唯一改變可見行為的步驟）

## Open Questions

- 敵機生成頻率／敵彈頻率／子彈速度／生命值無敵時間長度皆為拍腦袋估算，上線後建議實際玩幾局記錄存活時間與擊殺數分佈再校準（比照既有遊戲常數的 Follow-up 慣例）。
- coin 倍率（`coinRate: 0.2`，見 Decision 11 試玩後校準過的數值）是本次唯一「重新估算而非沿用既有遊戲」的倍率，實測後若跟其他遊戲的 coin/分鐘產出差距明顯，需要單獨校準。
- 道具掉落機率（基本／強化／里程碑敵機各自的掉落率）、連擊倍率門檻（5/12/24）、里程碑強敵門檻（每 200 分，見 Decision 11 調降後的數值）都是拍腦袋估算，上線後應依實測的「道具出現頻率體感」與「連擊維持難易度」調整。
- 是否要在 HUD 上額外顯示「剩餘生命」圖示（例如飛船小圖示 × 3）、目前連擊數與武器強化剩餘時間？屬於實作細節，留待實作階段決定，不影響本次架構規劃。
