## Context

11選5 是本專案第 6 個彩種，也是第 2 個「雙盤口 + 共用期別 + 共用彩池」的彩種（第 1 個是 SSC）。
來源 `bglottery src/components/room/lotteryAll/11x5/` 的結構與 `ssc/` 幾乎一模一樣
（`index.vue` + `index_script.js` 依 `mode` 切 `creditTraditional/creditPlay.vue`（信用）
或 `official/{tabs,play}.vue`（官方）），因此**信用盤可直接比照 SSC-CD 改**，
唯一差異是號碼域從「0~9 可重複」變成「1~11 不重複」。

官方盤則明顯比 SSC-OF／PK10-OF 複雜：多了「膽拖」（`DT2`~`DT8`）與「任選 N 中 M」
兩種本專案沒有先例的下注模式，故切成階段 2。

### 來源設定的資訊缺口與補齊方式

`config_11x5_credit.js` **只有 playId、沒有名稱也沒有賠率** —— 原專案的 `playName`／`maxPrize`
是由伺端 `LotteryPlayOdds` 回傳後，用 `index_script.js:205 mergeCreditData()` 併進本地 layout 的。
所以名稱必須由 UI 行為反推（`prompt/11x5.txt` §3 的指定做法），推導鏈如下：

1. **注項數量與 id 段落**（來源事實）
   - `第一球`~`第五球`（playTypeId 1121010~1121014）各 15 個注項，id 尾碼 `11`~`25`
   - `总和`（1121015）6 個注項，尾碼 `10`~`15`
   - `龙虎斗`（11211）每組球對 2 個注項，尾碼 `10`／`11`
   - `全5中1`（11212）11 個注項，尾碼 `10`~`20`
2. **前端把 15 個球位注項切成兩個分頁**（`creditPlay.vue:54,80`）
   - `v-if="+play.playName == play.playName"` → 純數字名稱那些進「1-5球」分頁
   - `v-if="+play.playName != play.playName"` → 非數字名稱那些進「兩面」分頁
   - 對照 `index_script.js:291 sscCredit()`：tab 11210 被拆成 `112100`（1-5球，playTypeList 前 5 個）
     與 `112101`（兩面，前 6 個 = 5 球位 + 總和）
   - ⇒ 15 = **11 個號碼（01~11，尾碼 11~21）+ 4 個兩面（尾碼 22~25）**
3. **兩面那 4 項是大／小／單／雙**，順序照本專案 `ssccd/plays.js` 既有慣例
   （SSC 兩面 id 尾碼 `10,11,12,13` = 大,小,單,雙）
4. **判定門檻全部有硬來源**：見 `proposal.md` 的規則表（`roadMap.vue` 的路珠計算式）

## Goals / Non-Goals

**Goals**
- 階段 1 交付可完整運作的 11x5 信用盤（下注 → 開獎 → 結算 → 領獎 → 爆池分配），並與窮舉機率對帳
- 賠率一律「公平賠率 × RTP」推導（`X5_RTP_FALLBACK = 0.97`），設定檔的 `odds` 只是快照
- 彩池接既有泛用骨架，**不新造**一套：`weight` 宣告在設定檔、結算時用 `(playKey, tabId, betCode)` 反查
- 期別／開獎號／共用彩池抽到 `x5Shared.ts`，讓階段 2 的官方盤直接接上、不用改動信用盤

**Non-Goals**
- 階段 1 不做官方盤（含膽拖）；`x5Of.ts`／`11x5-of.vue`／`x5of/` 留到階段 2
- 不做追號（`trace`）—— 既有彩種都沒做，來源有但本專案一律不實作
- 不做返水率滑桿（`rebateRate`）—— 同上，本專案賠率是固定 RTP 推導，沒有返水點概念
- 不改動既有彩種的判定、爆池或看板設定

## Decisions

### 1. 號碼域：1~11 取 5 個不重複，母數用「組合」還是「排列」要分清楚

同一個彩種有兩種母數，用錯就會算錯賠率：

| 判定對象 | 母數 | 用在 |
|---|---|---|
| 單一球位的號碼分布 | 11（該球位的邊際分布） | 單球號碼 1/11、單球大小單雙 |
| 兩球位的相對大小 | 2（對稱） | 龍虎鬥 龍/虎 各 1/2 |
| 5 碼的**集合**性質 | C(11,5) = **462** | 總和、全5中1、爆池條件、任選、猜中位、定單雙 |
| 5 碼的**排列**性質 | P(11,5) = **55,440** | （階段 2）直選類 |

⚠️ 邊際分布為什麼是均勻的：抽 5 個不重複號碼、位置隨機，任一球位落在任一號碼的機率都是 1/11
（超幾何分布的邊際均勻性）。所以單球號碼直接 1/11，不需要窮舉 55,440。
但**總和不能用邊際分布算**（5 個號碼不獨立），必須窮舉 462 種組合 —— 這是與 SSC
（號碼可重複、總和可用摺積）最大的差別，`x5.ts` 因此改成窮舉建表而非摺積。

窮舉結果（`X5_SUM_COUNTS`，合計 462，對稱於 30）：
```
15:1 16:1 17:2 18:3 19:5 20:7 21:10 22:12 23:16 24:19 25:23 26:25 27:29 28:30 29:32
30:32 31:32 32:30 33:29 34:25 35:23 36:19 37:16 38:12 39:10 40:7 41:5 42:3 43:2 44:1 45:1
```

### 2. 注碼採 descriptor 模式（比照 `ssc-cd.ts`，不用 `k3-cd.ts` 的正則堆疊）

`_parseBet(betCode) → X5Bet` 一個入口，`x5ChanceOf()`（機率）與 `x5IsHit()`（判定）
各自對同一個 descriptor 做 switch —— 新增玩法只會漏改一邊的風險比 `k3-cd.ts` 低。

```ts
type X5Bet =
  | { kind: 'ballNumber'; ball: number; num: number }        // 第一球07
  | { kind: 'ballSide'; ball: number; side: X5Side }         // 第一球大
  | { kind: 'sumSide'; side: X5SumSide }                     // 總和大 / 總和尾大
  | { kind: 'anyHit'; num: number }                          // 全中07
  | { kind: 'dragon'; a: number; b: number; side: '龍'|'虎' } // 龍虎12龍
```

注碼字串格式（= 設定檔的 `name`，`helpers._findTabItem()` 靠它反查）：

| 玩法 | 注碼 | 範例 |
|---|---|---|
| 1-5球 | `第N球` + 兩位數號碼 | `第一球07`、`第五球11` |
| 兩面（球位） | `第N球` + 大/小/單/雙 | `第三球大` |
| 兩面（總和） | `總和` + 大/小/單/雙/尾大/尾小 | `總和尾大` |
| 龍虎鬥 | `龍虎` + 兩個球位 + 龍/虎 | `龍虎12龍` |
| 全5中1 | `全中` + 兩位數號碼 | `全中07` |

⚠️ 號碼一律**補零兩位**（`01`~`11`）—— 11選5 的顯示慣例，且避免 `第一球1` 與 `第一球11`
在人眼上混淆。解析時 `Number(rest)` 收斂，所以 `第一球1` 也吃得下，但產生的一律是補零版。

### 3. 總和 6 個注項 = 大／小／單／雙／尾大／尾小（使用者拍板）

來源 `总和`（playTypeId 1121015）有 6 個 playId，但 `roadMap.vue` 只證實了大小（界線 31）與單雙 4 項。
剩下 2 項（尾碼 `14`/`15`）在來源無任何名稱或判定依據 —— **由使用者於提案階段確認為「尾大／尾小」**，
判定為「總和的個位數 ≥ 5 為尾大、≤ 4 為尾小」（11選5 通行定義）。

窮舉核對（母數 462）：

| 注項 | 命中 | 機率 | 公平賠率 | 賠率(×0.97) | weight |
|---|---|---|---|---|---|
| 總和大（≥31） | 215 | 46.5368% | 2.149 | 2.08 | 1 |
| 總和小（≤30） | 247 | 53.4632% | 1.870 | 1.81 | 1 |
| 總和單 | 236 | 51.0823% | 1.958 | 1.89 | 1 |
| 總和雙 | 226 | 48.9177% | 2.044 | 1.98 | 1 |
| 總和尾大（尾≥5） | 232 | 50.2165% | 1.991 | 1.93 | 1 |
| 總和尾小（尾≤4） | 230 | 49.7835% | 2.009 | 1.94 | 1 |

⚠️ 總和大小**不對稱**（215 vs 247），因為分佈對稱於 30 而界線切在 30/31，30 那 32 種歸小。
這是來源 `c < 31 ? '小' : '大'` 的直接結果，不是 bug，賠率也因此不同（2.08 vs 1.81）。

### 4. 爆池觸發條件：五球「全開單」或「全開雙」（7/462 ≈ 1.52%，使用者拍板）

既有彩種訂條件的兩條標準（寫在 `shared/config/k3-cd.ts:336-345`）：
1. 必須是看板上真的押得到的注項
2. 機率要與 6hc-cd 的「特別號開 49」（1/49 ≈ 2.04%）同量級

⚠️ **第 1 條在 11x5-CD 無法直接滿足** —— 這是與 eggs／ssc／k3 最大的差異：
11x5-CD 只有 1-5球／兩面／龍虎鬥／全5中1 四種玩法，**沒有任何一個注項的機率落在 1~2% 量級**，
最罕見的注項是「單球某號碼」1/11 = 9.09%。所以 eggs 那套「挑一個現成的罕見注項（豹子）」
的做法在這裡不可用，必須改用「看板注項的**概念**所組成的開獎特徵」。

候選窮舉（母數 462，全部精確值）：

| 候選 | 命中 | 機率 | 評估 |
|---|---|---|---|
| **全單或全雙** | **7** | **1.5152%** | **採用** —— 用的是每個球位都押得到的「單／雙」概念 |
| 全大或全小 | 7 | 1.5152% | 機率相同，落選（見下） |
| 五連號 | 7 | 1.5152% | 「連號」不是看板上任何注項的概念 |
| 總和 ≤17 或 ≥43 | 8 | 1.7316% | 「極值」不是注項（總和只有大小單雙尾大尾小） |
| 同一面（全大/小/單/雙） | 14 | 3.0303% | 偏頻繁，池養不起來 |
| 五球全小（1~6） | 6 | 1.2987% | 單邊條件，敘事不對稱 |
| 五球全大（7~11） | 1 | 0.2165% | 太罕見（大只有 5 個號，全大只有 1 種組合） |

**選「全單或全雙」而非「全大或全小」的理由**：兩者機率完全相同（皆 7/462），
但單雙的界定（奇偶）不依賴任何門檻常數，而大小依賴 `X5_BIG_LINE = 7` 這個來源推得的界線；
爆池條件綁在「不會因為門檻調整而改變」的性質上比較穩。
分解：全單 = C(6,5) = 6 種（1,3,5,7,9,11 取 5）、全雙 = C(5,5) = 1 種（2,4,6,8,10）。

```ts
export const X5_JACKPOT_SETTINGS: JackpotSettings = {
  rakeRatio: 0.01,
  payoutRatio: 0.5,
  minPool: 1000,              // 以 rakeRatio 1% 換算 ≈ 需累積 10 萬投注額
  weightFallback: 1,
  boardWeight: { cd: 1, of: 1 },
  hitLabel: '五球全開單或全開雙',
  hitRate: 7 / 462
}
```

⚠️ **沒有「雙重加成」問題**：eggs／k3／ssc 的爆池條件同時是 weight 最高的注項（押中者拿賠率又拿最大份），
11x5 的爆池條件不對應任何單一注項，所以不存在這個副作用，`plays.js` 不需要任何 `weight: 0` 的排除。

### 5. weight 分級：沿用 6hc 的理論賠率分級法

規則見 `shared/config/6hc-cd.ts:1836-1846`：依理論賠率 `1 / 命中機率` 分三級
`≥20 → 3`、`2.5~20 → 2`、`<2.5 → 1`。逐項套用到 11x5-CD 的 112 個注項：

| 分頁 | 注項 | 命中機率 | 理論賠率 | weight |
|---|---|---|---|---|
| 1-5球 112100 | 第一~五球 01~11（55 項） | 1/11 | 11.000 | **2** |
| 兩面 112101 | 第N球大（5 項） | 5/11 | 2.200 | 1 |
| 兩面 112101 | 第N球小（5 項） | 6/11 | 1.833 | 1 |
| 兩面 112101 | 第N球單（5 項） | 6/11 | 1.833 | 1 |
| 兩面 112101 | 第N球雙（5 項） | 5/11 | 2.200 | 1 |
| 兩面 112101 | 總和 6 項 | 見決策 3 | 1.87 ~ 2.15 | 1 |
| 龍虎鬥 11211 | 龍／虎（20 項） | 1/2 | 2.000 | 1 |
| 全5中1 11212 | 全中 01~11（11 項） | 5/11 | 2.200 | 1 |

⇒ **只有「1-5球」那 55 個號碼注項是 weight 2，其餘 57 項一律 weight 1，沒有 weight 3**
（11x5-CD 最高理論賠率只有 11 倍，達不到 ≥20 的門檻）。
group 層預設值：1-5球 分頁的 5 個群組設 `weight: 2`，其餘群組設 `weight: 1`；
item 層仍逐項標上明確 weight（同 ssccd 慣例，讓對帳時一眼看得到）。

### 6. 分頁 id 沿用來源前端切分後的 id

來源的 `playTabId` 只有 3 個（11210 整合／11211 龍虎斗／11212 全5中1），
但 `index_script.js:291` 的 `sscCredit()` 把 11210 拆成 `112100`（1-5球）與 `112101`（兩面）兩張分頁，
玩家實際看到的是 4 張。本專案採**玩家看到的 4 張**為 tabId：

| playKey | tabId | tabName | 群組 | 注項數 |
|---|---|---|---|---|
| `ball` | 112100 | 1-5球 | 第一~五球 | 55 |
| `liangmian` | 112101 | 兩面 | 第一~五球 + 總和 | 26 |
| `longhu` | 11211 | 龍虎鬥 | 10 組球對 | 20 |
| `quan5` | 11212 | 全5中1 | 全5中1 | 11 |

`playId` 格式 `${tabId}-${來源playId}`（例：`112100-112101011` = 第一球01）。
⚠️ 與 SSC 不同，11x5 來源的每個注項本來就有唯一 playId，
**不需要** SSC 那種「再接球位與號碼讓它唯一」的補救（`ssccd/plays.js` 檔頭第 19 條註解）。

### 7. `x5Shared.ts`：期別、開獎號與共用彩池

比照 `sscShared.ts`：module 級單例，持有當日期表、開獎號、共用彩池（官方盤在吃），
並負責「等兩個盤口都交件才結算共用彩池」的編排。
階段 1 只有信用盤接上，但**Shared 層照建** —— 因為期別與開獎號本來就該是兩盤口共用的單一真相，
階段 2 要接官方盤時不必回頭改信用盤（eggs 沒建 Shared 是因為它永遠只有一個盤口，情況不同）。

金流兩條獨立的線（比照 `sscCd.ts`）：
```
下注  playBets()          → issueJackpotMap[issue] += amount * rakeRatio
開獎  settleIssuePrize()  → pool = issueJackpotMap[issue] + carryJackpot
                          → triggered ? 發 pool * payoutRatio : 全部滾存
                          → carryJackpot = jackpot.remain；issueJackpotMap[issue] = 0
```
⚠️ 爆池池（`X5_JACKPOT_SETTINGS`）與 Shared 的共用彩池（官方盤直選在吃）是**兩個獨立的池**，
各自抽水、互不相吃 —— 同 `ssc-cd.ts:368` 的註解。

## Risks / Trade-offs

- **[Risk]** 總和「尾大／尾小」是使用者拍板、非原始碼依據（來源只有 playId）。
  → **Mitigation**：判定寫成 `x5.ts` 的具名常數 `X5_SUM_TAIL_BIG_LINE = 5` 並註明「使用者確認」，
    要改只需改一處；`plays.js` 的注項名稱與 `x5-cd.ts` 的解析同步。
- **[Risk]** 爆池條件不對應任何單一注項，玩家在看板上看不到「押這一項就會觸發爆池」。
  → **Mitigation**：`DialogRule.vue` 用 `hitLabel`／`hitRate`／`payoutRatio`／`minPool` 動態渲染說明，
    明確寫出「爆池由開獎結果觸發，全期有效注單依 weight 分配」，不讓玩家誤以為要押特定注項。
- **[Risk]** 觸發率 1.52%／期，自然開出要等很久，端到端驗證會卡住。
  → **Mitigation**：比照 eggs 的做法，用臨時探測路由強制以 `1,3,5,7,9`（全單）呼叫真實的
    `settleIssuePrize()` 驗完即刪（`eggs-jackpot-plan.md` §7 已有先例）。
- **[Trade-off]** 階段 1 建了 `x5Shared.ts` 但只有一個盤口在用，短期看像多餘的抽象。
  → 選擇理由：期別與開獎號是兩盤口共用的單一真相，階段 2 一定會用到；
    若階段 1 先塞進 `x5Cd.ts` 再抽出，等於要動已驗證過的結算路徑，風險更高。

## Migration Plan

全新彩種，無既有資料需要遷移。

1. 依 `tasks.md` 由 config → server → 前端依序實作，每層各自驗證（窮舉對帳腳本／curl／`npm run dev`）
2. 階段 1 完成後跑完整流程：登入 → 下注多筆（含 weight 1 與 weight 2）→ 開獎 → 結算 → 領獎 → 對帳餘額
3. 爆池以臨時探測路由強制觸發驗證，測完刪除路由
4. 中止時可直接刪除新增檔案並回退 `constants.js`／`storage.ts`／`api.ts`／`lottery-hall.vue`／
   `BgAutoPanel.vue`／`useBgAutoActive.ts` 的追加段落（皆為追加式修改）
