## Context

玩法來源：`bglottery` `src/components/room/lotteryAll/kl10/`（**不是** `11x5/`、也不是 `kl8/`，
三者是獨立彩種資料夾）。該資料夾只有信用模式，4 個玩法分頁：

| playTabId | 名稱 | 來源檔 | 內容 |
|---|---|---|---|
| 13210 | 正和（1-8球） | `allTraditional/zhenghe/config_zhenghe.js` | 第一~第八球 ×（單碼 ＋ 兩面 8 面） |
| 13211 | 龍虎鬥 | `allTraditional/lhd/config.js` | 28 組「第X球VS第Y球」× 龍/虎 |
| 13212 | 任選 | `allTraditional/renxuan/config_play.js` | 任一中一 ~ 任五中五 |
| 13213 | 兩面 | `allTraditional/liangmian/config.js` | 和值 6 面 ＋ 上下盤 3 項 ＋ 奇偶盤 3 項 |

### 來源查證結果（動工前必須釐清的三個疑點，皆已查證）

1. **球號範圍＝1~20、一期 8 球**（不是 `dict.js` 的 0~27）
   - `zhenghe/play_script.js` 的 `mergeCreditData()` 用 `for (let n = 1; n <= 20; n++)` 展開單碼池
   - `renxuan/play_script.js` 的 `doCreatePlayData()` 同樣 `for (let i = 1; i <= 20; i++)`
   - `index_script.js` 與 `header.vue` 的開獎號預設值都是 `'?,?,?,?,?,?,?,?'`（8 個）
2. **`dict.js` 是 pceggs 殘留、kl10 沒有色波玩法**
   - 內容是 0~27 的紅/藍/綠/灰四色表（與 `shared/config/eggs.ts` 的 `EGGS_WAVE_MAP` 完全相同）
   - `grep -rn "dict" kl10/` **零命中** —— kl10 底下沒有任何檔案 import 它
   - 4 個 config 也沒有任何色波 playId → 本次不實作色波
3. **任選不能照抄六合彩連碼**
   - `renxuan/config_play.js` 檔頭雖寫「複製自六合彩-連碼」，但那只是 config 結構被複製
   - 判定對象是「所選號碼是否全部落在 8 個開獎號內」（號碼池 20、開獎 8），
     與六合彩連碼（號碼池 49、開獎 7）的母數完全不同，必須自行窮舉
   - `doCalcCombination(selected, minChosen)` 說明複式如何拆單：從已選 k 個號碼中取
     C(k, N) 種組合，每種組合各成一注（N＝該分頁的 `minChosen`）

### 來源沒有的資訊（賠率與判定門檻）

`bglottery` 的注項名稱／賠率是伺端 `LotteryPlayOdds` 回傳後才併進本地 layout 的
（`mergeCreditData()`），前端 config 只有 playId。走勢頁 `trend/trend.vue:87` 可看到
kl10 的 `datasExt` 會出現 `大 / 小 / 單 / 雙 / 上 / 和 / 奇 / 偶 / 總尾大` 等字樣，
證實這些開獎特徵存在，但**判定式在伺端、前端查不到**。

因此以下三項由使用者於提案階段拍板（記錄於本檔，實作時全部收斂成具名常數）：

| 項目 | 拍板結果 | 機率（C(20,8)=125,970 窮舉） |
|---|---|---|
| 8 球總和大小界線 | **≥84 大、<84 小**（無和局） | 大 64,879（51.5035%）／小 61,091（48.4965%） |
| 上下盤／奇偶盤 | **比個數多寡，4:4 為和盤** | 上/下/奇/偶 各 40,935（32.4958%）、和盤 44,100（35.0083%） |
| 爆池觸發條件 | **奇數 ≥7 個或偶數 ≥7 個** | 2,490（1.9767%） |

其餘門檻沿用本專案既有慣例，不另發明：
- 單球大小界線 `KL10_BIG_LINE = 11`（1~20 對半分，大 10 個／小 10 個，與 x5 的 `X5_BIG_LINE` 同一個角色）
- 尾大／尾小界線 `KL10_TAIL_BIG_LINE = 5`（個位 ≥5 為尾大，比照 `X5_SUM_TAIL_BIG_LINE`）
- 合單／合雙＝號碼十位＋個位之和的奇偶（合數玩法的通行定義；1~20 剛好各 10 個）

## Goals / Non-Goals

**Goals:**
- 依 `kl10.ts`（機率核心）→ `kl10-cd.ts`（判定＋賠率＋爆池）→ `kl10cd/{plays.js,helpers.ts}`（看板設定）
  → `server/.../kl10.ts`（單一信用盤 service）→ `useKl10.ts` → `components/lottery/bg/kl10/**`
  → `pages/lottery/bg/kl10.vue` 的分層，完整複刻 EGGS 一套。
- 賠率一律「公平賠率（母數 ÷ 命中數）× RTP」推導，不寫死拍板數字。
- 爆池接既有 `shared/config/jackpot.ts` 骨架，weight 以「設定檔宣告 → 結算反查」關聯玩法。

**Non-Goals:**
- 不建立官方盤（OF）、不建 `kl10Shared.ts`（沒有共用對象）。
- 不實作色波（來源殘留檔，kl10 無此玩法）。
- 不改動既有彩種的判定與結算邏輯。

## Decisions

### 1. 母數分三種，用錯就會算錯賠率

| 判定對象 | 母數 | 用在 |
|---|---|---|
| 單一球位的號碼分布 | 20（邊際分布均勻） | 正和的單碼 1/20、單球兩面 10/20 |
| 兩球位的相對大小 | 2（對稱、無和局） | 龍虎鬥 龍/虎 各 1/2 |
| 8 碼的**集合**性質 | C(20,8) = 125,970 | 總和 6 面、上下盤、奇偶盤、任選、爆池 |

⚠️ 邊際均勻性同 x5：抽 8 個不重複號碼、位置隨機，任一球位落在任一號碼的機率都是 1/20，
所以單球類不必窮舉排列數 P(20,8)。
⚠️ 總和**不能**用邊際分布算（8 個號碼不獨立），必須建表；
但為了不在記憶體裡放 125,970 × 8 的陣列，`kl10SumCounts()` 用遞迴累加建表、**不保留組合本身**。
上下盤／奇偶盤／爆池則用「一半 10 個號碼」的組合數閉式 `C(10,k) × C(10,8-k)` 直接算，
不需要窮舉（`kl10HalfSplitCounts()`）。

### 2. 注碼格式（`_parseBet` 是唯一解析入口，比照 ssc-cd / x5-cd）

```
正和    第一球07 / 第一球大 / 第一球合單 / 第一球尾大      （球位前綴 + 號碼或 8 面之一）
龍虎鬥  龍虎12龍 / 龍虎78虎                              （兩個球位編號皆 1~8，必須遞增）
任選    任一中一07 / 任三中三03,07,15                     （分頁名 + 逗號分隔號碼，個數須等於 N）
兩面    總和大 / 總和尾大 / 上盤 / 上下和 / 奇盤 / 奇偶和
```

⚠️ 來源的上下盤與奇偶盤**兩組都有一個叫「和盤」的注項**，注碼必須唯一，
因此改名為 `上下和`／`奇偶和`（看板顯示也用同一個字串，避免看板與注單不同名）。
⚠️ 任選是本專案第一個「一注多碼」的信用盤玩法：注碼帶號碼組合，
`kl10cd/helpers.ts` 的注項查找因此要多一段「前綴比對」（見決策 4）。

### 3. 任選的複式展開放在前端 composable

來源 `renxuan/play_script.js` 就是在前端把「已選 k 個號碼」展開成 C(k, N) 注再送單
（`genFlattenBetList()` → `doCalcCombination()`）。本專案沿用同一個切法：
`useKl10` 的 `fetch.betsRenxuan()` 產生組合、每個組合一注（各自 `betCode`／`coin`／`odds`），
伺端仍然是「一注一注驗、一注一注派彩」，不需要為任選開特例。
好處是 `orders.ts`／`settleIssuePrize()`／爆池分配完全不用改。

### 4. 看板設定的注項查找要支援「動態注碼」

`kl10cd/helpers.ts` 的 `_resolveItem()` 兩段式：
1. 先照 EGGS 的做法比對 `playId` / `name`（正和、龍虎鬥、兩面都是靜態注項）
2. 找不到時，若注碼以某注項名稱開頭（任選的 `任三中三` + 號碼），視為該注項
   —— 這樣賠率、限額、爆池 weight 都能沿用同一組解析。

⚠️ `kl10HasBetCode()` 除了要「注項存在」，還要 `kl10ChanceOf(betCode) !== null`：
任選的號碼個數／範圍／重複只有判定層驗得出來，光靠設定檔比對會放行 `任三中三03,03,03`。

### 5. 爆池：接骨架，不新發明

- 觸發條件「奇數 ≥7 或偶數 ≥7」＝ 2,490/125,970 ≈ 1.9767%，與 6hc-cd 的「特別號開 49」
  （2.04%）同量級，符合 `k3-cd.ts` 訂的量級標準。
- 為什麼不挑一個現成注項當條件：kl10 看板最罕見的靜態注項是單碼 1/20 = 5%，
  任選雖有 1.44%（任四中四）與 0.36%（任五中五），但那是**注單**的中獎率、不是開獎特徵
  （任何一期都必然存在 C(8,4)=70 組中獎的任四中四），不能當爆池期判準。
- 為什麼是奇偶而不是上下：兩者機率完全相同（各 2,490），但奇偶只依賴號碼奇偶、
  不依賴任何門檻常數；上下盤依賴「1~10／11~20」這條半分線。理由與 x5 選「全單全雙」一致。
- 「全奇或全偶」（8:0）只有 90/125,970 ≈ 0.07%，比基準低 28 倍，平均 1,400 期才觸發一次，故不採用。
- 沒有「雙重加成」問題：條件不對應任何單一注項，`plays.js` 不需要任何 `weight: 0` 排除。

### 6. weight 分級沿用 6hc 的理論賠率法（`1/命中機率`：≥20→3、2.5~20→2、<2.5→1）

| 分頁 | 注項 | 理論賠率 | weight |
|---|---|---|---|
| 正和 · 單碼 | 01~20 | 20.000 | 3 |
| 正和 · 兩面 | 大/小/單/雙/合單/合雙/尾大/尾小 | 2.000 | 1 |
| 龍虎鬥 | 龍/虎 | 2.000 | 1 |
| 任選 | 任一中一 | 2.500 | 2 |
| 任選 | 任二中二 | 6.786 | 2 |
| 任選 | 任三中三 | 20.357 | 3 |
| 任選 | 任四中四 | 69.214 | 3 |
| 任選 | 任五中五 | 276.857 | 3 |
| 兩面 · 和值 | 大 1.942／小 2.062／單 2.003／雙 1.997／尾大 2.001／尾小 1.999 | <2.5 | 1 |
| 兩面 · 上下盤 | 上盤/下盤 3.077、上下和 2.856 | 2.5~20 | 2 |
| 兩面 · 奇偶盤 | 奇盤/偶盤 3.077、奇偶和 2.856 | 2.5~20 | 2 |

⚠️ 群組層給預設、注項層覆寫；明確 `weight: 0` 代表排除在爆池外，與「沒設定」（退回
`weightFallback`）是兩件不同的事，判斷一律用 `== null`（`jackpot.ts` 也守一次）。

### 7. 元件目錄不分 `cd/`／`of/`；任選另開一支看板

依 `openspec/project.md` 的分層標準（「會不會被兩個盤口同時用到」），kl10 永遠只有一個盤口，
元件平鋪在 `app/components/lottery/bg/kl10/{base,block,block/footer}/`。
唯一與 EGGS 不同的是多一支 `base/BoardRenxuan.vue`：任選是選號池 → 組合展開，
互動模型（選幾個、展開幾注、總額）與「一注項一金額」的表格看板完全不同，
硬塞進同一支會讓 `Board.vue` 長出兩套狀態機。

## Risks / Trade-offs

- **[Risk]** 總和大小界線、上下盤／奇偶盤定義、爆池條件皆為使用者拍板，非原始碼依據。
  → **Mitigation**：全部收斂成 `shared/config/kl10.ts` 的具名常數（`KL10_SUM_BIG_LINE`、
    `KL10_HALF_LINE`、爆池門檻 `KL10_JACKPOT_LOPSIDED_MIN`）並附「使用者拍板」註解，改一處即全站生效。
- **[Risk]** 任選複式展開在前端 → 惡意端可送出任意注碼組合。
  → **Mitigation**：伺端 `validateBetQuota()` 對每一注都跑 `kl10HasBetCode()`（含判定層的號碼驗證），
    任一注不合法整筆拒單；賠率也由伺端用 `kl10TabOddsOf()` 重算後才鎖進注單，不吃前端傳來的值。
- **[Risk]** 任選複式一次可能展開很多注（例如任二中二選 8 個號碼 = 28 注），
  單注限額過得去但總額暴增。
  → **Mitigation**：沿用既有的「單期分頁上限」（`settings.quota.issue.max`）擋總額；
    前端在送單前顯示注數與總額。
- **[Risk]** `kl10SumCounts()` 要跑遞迴建表（125,970 條路徑）。
  → **Mitigation**：memoize，一個 process 只算一次；且不保留組合陣列（只累加計數），
    記憶體是 97 個整數而非 10MB。

## Migration Plan

全新彩種，無既有資料需要遷移。步驟：
1. 依 `tasks.md` 由 config → server → 前端依序實作，每層各自驗證（esbuild + node 對帳、curl、`npm run dev`）
2. 全部完成後跑一次端到端：登入 → 四個分頁各下注 → 等開獎 → 對帳派彩與爆池抽水／滾存
3. 中止時可直接刪除新增檔案，並回退 `constants.js`／`storage.ts`／`api.ts`／`lottery-hall.vue`／
   `BgAutoPanel.vue`／`useBgAutoActive.ts` 的追加段落（皆為追加式修改）
