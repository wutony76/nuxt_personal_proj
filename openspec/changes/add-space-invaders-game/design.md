## Context

- `add-game-history` 已建立 game-hall 小遊戲的完整架構：client 頁面自包含（engine class + reactive 鏡像 snapshot 或單一 reactive state）＋ `useGameHistory`（A/B 雙模式）＋ server 端 `RETRO_GAME_BASE`（共用基底＋每款遊戲一個服務檔＋每款遊戲一組 API 路由資料夾）。
- 現有 9 款遊戲裡，`SPACE SHOOTER`（`app/pages/game/space-shooter.vue`）是最接近的先例：都是俯視角、玩家左右移動＋射擊＋閃避、生命值機制（3 條命＋短暫無敵＋重生）。但 SPACE SHOOTER 的敵機是「持續生成、各自獨立移動」（比照 `add-space-shooter-game` Decision 2 的選擇），SPACE INVADERS 要做的是傳統版「固定隊形整批同步移動」，兩者的敵機資料結構與移動邏輯完全不同，不能直接沿用 SPACE SHOOTER 的敵機生成器，只能沿用其「生命值＋無敵＋重生」與「玩家子彈 vs 敵機、敵彈 vs 玩家」兩組獨立碰撞判定的既有做法。
- 本次首度引入三個全新機制：（1）**隊形同步移動＋隨存活數量加速**、（2）**可被打爛的防禦掩體（多格可摧毀地形）**、（3）**玩家同時最多 1 發子彈**（其餘 9 款遊戲要嘛沒有子彈、要嘛都是固定射速連發）。這三項都是傳統《太空侵略者》的標誌性機制，也是這款遊戲存在的理由——如果不做這三項，就只是換皮的 SPACE SHOOTER。
- 現有遊戲的計分方向多數是「越多分越高、開放式無上限」（比照 racing/runner/tetriminos/match3/spaceShooter），只有 PONG（勝場數）與 MINESWEEPER（5 關封頂總分）是例外。SPACE INVADERS 延續「開放式無上限」的多數慣例，不屬於第三個特例。

## Goals / Non-Goals

**Goals:**
- 提供傳統《太空侵略者》核心體驗：固定隊形艦隊整批同步移動、碰邊界下降並加速、掩體防禦、玩家單發子彈限制、UFO 神秘獎勵分。
- 波次制（清空一波即進入下一波，難度遞增），分數開放式無上限，跟 SPACE SHOOTER／snake／racing 等多數遊戲的計分哲學一致。
- 生命值機制（3 條命）沿用 SPACE SHOOTER 已驗證的「扣命＋短暫無敵＋重生」做法，不重新設計。
- Server 端、client 資料層、game-hall 入口完全比照既有九款遊戲的慣例逐一擴充，不引入新的資料庫或跨遊戲共用邏輯。

**Non-Goals:**
- 不做關卡選擇／自訂難度／自訂隊形大小，隊形規模（5×8）與波次遞增規則皆為固定常數。
- 不做多人合作／對戰。
- 不引入資料庫；server 端持久化沿用專案現況的 in-memory 作法。
- 不做遊戲重播，只存結算後的摘要（分數、等級/波次）。
- 不修改既有 `MINESWEEPER`／`SPACE SHOOTER` 的任何程式碼或資料。

## Decisions

1. **敵機採「單一隊形物件＋成員陣列」，整批同步移動，而非比照 SPACE SHOOTER「各自獨立生成與移動」**
   - 理由：這是傳統版與 SPACE SHOOTER 最根本的差異所在。用一個 `formation` 物件維護「整體位移 offsetX／offsetY」＋「當前移動方向 dir」＋「成員陣列（每個成員只存 row/col 邏輯座標與存活狀態，不需要各自的 vx/vy）」，比照矩陣式管理，移動時只需更新 `formation.offsetX`，所有存活成員的畫面座標＝`baseX(col) + offsetX`，不需要逐一計算每個敵機的獨立速度。
   - 做法：`step()` 每隔 `moveIntervalTicks` 執行一次「整批位移」：`offsetX += stepSize * dir`；若最右／最左存活成員超出邊界，則 `offsetY += ROW_DROP`、`dir *= -1`，同時（傳統版特徵）縮短下一次 `moveIntervalTicks`。

2. **移動節奏「剩餘存活敵機越少、interval 越短」，用固定對照表而非連續函式**
   - 理由：這是原作最著名的緊張感來源（早期步伐緩慢，只剩少數敵機時速度暴衝）；比照原作精神但簡化為可調的固定對照表，避免為了精確重現原始像素節奏而過度設計連續公式。
   - 做法：`MOVE_INTERVAL_BY_ALIVE_RATIO`，例如存活比例 `>0.8` → 42 ticks／`>0.5` → 30 ticks／`>0.2` → 18 ticks／其餘 → 8 ticks（皆為 `TICK_MS=16ms` 為單位，可在實作時依手感微調）；每次有敵機被擊落後重新查表更新目前的 `moveIntervalTicks`。

3. **玩家子彈：同時最多 1 發，比照原作核心限制，而非沿用 SPACE SHOOTER 的固定射速連發**
   - 理由：這是傳統版「射擊節奏」的核心特徵之一，強迫玩家精準抓時機而非無腦連發，也是與 SPACE SHOOTER 差異化的重要一環。
   - 做法：`state.playerBullet: Bullet | null`（不是陣列）；按下開火鍵時若 `playerBullet` 已存在則忽略，只有在該發子彈擊中目標或飛出畫面上緣、被設回 `null` 後才能再次開火。

4. **敵機還擊：每欄僅最前線（該欄目前最底部存活）成員可開火**
   - 理由：比照原作「只有最下排會射擊」的規則，同時避免「全部敵機都能開火」造成子彈滿天飛、無從閃避的失衡體感。
   - 做法：`step()` 內先算出「每欄目前存活的最大 row（即最前線）」集合，每個 tick 以低機率（隨波次提升）從這個集合中隨機挑一個成員發射一顆敵彈；一欄如果已經清空則不再有敵彈來源。

5. **防禦掩體（Bunker）：4 座、各自為可獨立摧毀的格子陣列，敵機本體與雙方子彈都能摧毀掩體格子**
   - 理由：掩體是傳統版另一個標誌性機制，也是本次唯一「地形會隨遊戲進行被永久破壞、且會影響雙方（玩家與敵機）互動」的系統，需要獨立於「角色 vs 角色」碰撞之外的「拋射物／敵機 vs 地形」碰撞。
   - 做法：`Bunker = { id, x, y, cells: boolean[][] }`（例如 5×3 的小格陣列，代表一座掩體的像素方塊圖案），4 座掩體固定分佈在玩家前方；`step()` 內對「玩家子彈」「敵彈」「敵機隊形位移後的新座標」三者分別檢查是否與任一 `cells[r][c] === true` 的格子重疊，重疊即把該格設為 `false`（摧毀，且消耗掉那顆子彈／不阻擋敵機移動，敵機只是路過順便打爛地形）；掩體格子全滅的掩體視為消失，不需要特殊處理。

6. **UFO：獨立於一般敵機隊形之外的裝飾＋獎勵物件，不參與隊形碰撞與敵機還擊邏輯**
   - 理由：UFO 在原作中是純粹的「額外目標」，不下降、不開火、不影響隊形是否觸底的判定，把它做成完全獨立的可選物件可以避免污染隊形/掩體/子彈這三組核心碰撞邏輯。
   - 做法：`state.ufo: { x, y, bonus } | null`，每隔隨機一段時間（例如 20~40 秒）從畫面上緣一側水平飛到另一側後消失；玩家子彈與 `ufo` 重疊時給予隨機獎勵分（50/100/150/300 等機率分佈）並移除 UFO、消耗該發子彈，不需要检查 UFO 是否會被敵彈或隊形影響。

7. **即死條件（非扣命）：任一存活敵機的畫面 y 座標超過「掩體列以下的底線」時，直接結束遊戲**
   - 理由：這是傳統版「打不完就輸」的核心緊張感來源，獨立於生命值系統之外——玩家可能還有 2 條命，但只要隊形推進到底線就必須立刻結束，這跟「被擊中扣命」是兩套獨立的結束判定，需要在 `step()` 內明確分開檢查，避免跟生命值歸零的結束流程混用同一個 flag。
   - 做法：每次隊形整批下降（`offsetY += ROW_DROP`）後，檢查是否有任一存活成員的 `y >= DEATH_LINE_Y`；是則立即呼叫既有的 `finishGame()` 流程，用目前累積分數結算，不論當下剩餘生命數為何。

8. **波次制：清空當前隊形即進入下一波，隊形重新滿編從頂部開始，基礎移動速度與敵機開火機率隨波次遞增；分數開放式無上限**
   - 理由：延續原作「一波接一波、越後面越難」的設計，同時保持跟 snake/racing/runner/spaceShooter 一致的「開放式無上限、越打越久分越高」計分哲學，不採用 MINESWEEPER 式的固定關卡封頂總分。
   - 做法：`state.wave` 從 1 起算，`formation` 全滅時 `wave += 1`、重建滿編隊形（起始 `offsetY` 重置為 0）、`baseMoveIntervalTicks` 與敵機開火機率依 `wave` 提高一個固定梯度；玩家生命值、分數、掩體損毀狀態**不**隨波次重置（掩體不修復，累積耗損比照原作精神，只是原作是每一輪都重置掩體，這裡刻意選擇「不修復」以維持長局的張力遞增，屬於本次的簡化取捨）。

9. **計分依敵機所在列給分（列數越高、越接近頂端分越高）＋ UFO 隨機獎勵分，coin 倍率獨立估算**
   - 理由：比照原作「後排分數低、前排分數高」的既有設計精神，同時延續 SPACE SHOOTER／tetriminos 的「事件觸發加分」計分模型，而非 racing/runner 的「持續時間累加」。
   - 初始估算：由上到下 5 列基礎分數 `[40, 40, 30, 20, 10]`（可在實作時依隊形實際列數微調），UFO 隨機獎勵 `[50, 100, 150, 300]`；預期一場中高水準對局（多波次、UFO 命中幾次）總分落在 800～2000 區間，比照 SPACE SHOOTER 校準方式抓 `coinRate: 0.3`、`coinCapPerRun: 300`（沿用九款遊戲中八款的既有預設，不比照 SPACE SHOOTER 的特例 2500，因為本次沒有連擊倍率／道具加成會放大分數增速，不需要那麼高的單局上限）、`coinDailyCap: 100000`（沿用既有慣例）、`maxReasonableScore(): 8000`（需高於 `coinCapPerRun ÷ coinRate = 300 ÷ 0.3 = 1000`，留足夠寬裕的防偽造上限）。
   - 這些是估算值，上線後應依實測分數分佈校準，不影響架構本身。

10. **Server／API／client 資料層完全比照既有慣例擴充，不做任何架構調整**
    - `RETRO_GAME_BASE` 不變、`server/api/games/retro/<game>/history.*` 資料夾樣式不變、`app/services/api.ts` 的 `api.games.retro.*` 命名方式不變、`useGameHistory.ts` 的 `GAME_KEYS`／`_handlers.gameApi()` switch 擴充一個分支即可。
    - `gameKey` 採用 `'spaceInvaders'`（camelCase，比照 `spaceShooter` 的既有複合字 key 命名慣例），路由路徑採 `space-invaders`（kebab-case，比照既有路由資料夾命名風格）。

## Risks / Trade-offs

- [風險] 隊形同步移動＋加速對照表的手感可能跟原作預期落差大（太快/太慢）——因應：`MOVE_INTERVAL_BY_ALIVE_RATIO` 是獨立常數表，上線後可單獨微調，不影響架構。
- [風險] 掩體「不隨波次修復」是刻意簡化，長局玩到後期可能完全沒有掩體可用、難度曲線變陡——因應：這是已知取捨（見 Decision 8），先讓機制跑起來，若實測體感太差，之後可改成「每波次修復到一定比例」而不需要更動掩體資料結構。
- [風險] 玩家單發子彈限制＋敵機還擊機率若估算不當，可能太簡單（几乎不會被擊中）或太難（子彈打不完就先被清空生命值）——因應：比照既有遊戲做法，先讓機制跑起來，上線後依實測調整常數。
- [風險] 掩體格子碰撞需要對 3 種來源（玩家子彈／敵彈／敵機本體）分別檢查，邏輯複雜度略高於現有遊戲的「單一物件 vs 單一角色」碰撞——因應：三組檢查彼此獨立、互不影響，逐一實作與測試即可，不需要新的碰撞演算法（比照既有「固定 x/y 範圍矩形相交」判定手法）。
- [風險] coin 倍率是估算值，可能跟其他遊戲的 coin/分鐘產出有落差——因應：`coinRate`／`maxReasonableScore` 是獨立於 `spaceInvaders.ts` 的常數，上線後可單獨調整。

## Migration Plan

- 全新功能，無既有資料需要遷移，刻意設計成獨立的 `gameKey`，不影響既有九款遊戲的紀錄與 coin 上限，且完全不觸碰 `MINESWEEPER`／`SPACE SHOOTER` 的程式碼。
- 部署順序（每一步都可獨立回滾，比照既有幾次擴充的分步策略）：
  1. Server 端服務層與 `storage.ts` 註冊（尚未被路由引用，無風險）
  2. Server 端 API 路由（存在但尚未被前端呼叫，無風險）
  3. Client `app/services/api.ts` 擴充
  4. `useGameHistory.ts` 擴充
  5. 遊戲頁面 `app/pages/game/space-invaders.vue`（此步驟起才有實際資料寫入行為）
  6. `game-hall.vue` + `GameMachineCard.vue` + `GameHistoryDialog.vue`（此步驟起使用者才看得到入口，是唯一改變可見行為的步驟）

## Open Questions

- 隊形加速對照表、敵機開火機率、UFO 出現間隔與獎勵分機率分佈皆為拍腦袋估算，上線後建議實際玩幾局記錄存活時間與波次分佈再校準。
- 掩體「不隨波次修復」的取捨（見 Decision 8）如果實測體感太差，是否要改成「每波次修復到一定比例」？留待實測後決定。
- 是否要在 HUD 上額外顯示「目前波次」「剩餘敵機數」？屬於實作細節，留待實作階段決定，不影響本次架構規劃。
