# Engineering Evidence：大廳彩池首次揭示動畫

## 變更摘要

- **對應變更**：`fix-lottery-hall-pool-reveal-flash`
- **Commit**：`6b09cf9`、`c49bc57`
- **變更檔案**：`app/pages/lottery-hall.vue`

### 背景

大廳頁改成 SSR（`add-ssr-lottery-hall-pools`）後，HTML 一送出就是正確的彩池金額，原本「數字從 0 跳到實際值」的動畫就沒了。`abca4c5` 把動畫補回來，做法是在 `onMounted` 把數字歸零再爬升，結果產生三個問題：

1. **閃爍**：使用者看到的是 SSR 的正確數字 → 突然歸零 → 4 秒後爬回來，看起來像資料被丟掉重算。
2. **client 端切換頁面時沒有動畫**：`useAsyncData` 設了 `lazy: true`，`onMounted` 執行時資料還沒到，資料到了以後是直接賦值。
3. **settled 時間回到約 4.4 秒**。

### 修法

- **不從 0 起跑**：從目標值的 80~90% 開始爬升，每張卡片隨機取比例，避免所有卡片動作同步。
- **首次揭示用獨立的動畫時長**：新增 `POOL_REVEAL_ANIM_MS = 2000`，只用在首次揭示；10 秒輪詢拿到新數字時仍沿用 `POOL_ANIM_MS = 4000`。
- **client 端切換頁面也有動畫**：`watch(initialPools)` 用 `mounted` 旗標區分兩種情況。
  - 掛載前（SSR / hydration）：直接賦值。
  - 掛載後資料才到（lazy）：跑首次揭示動畫。

### 調整過程

| 版本 | 起跑點 | 時長 | settled 中位數 | 結果 |
|---|---|---|---|---|
| `abca4c5` | 0% | 4000ms | ~4.4s | 歸零閃爍 |
| 嘗試 1 | 90~95% | 4000ms | ~4483ms | 閃爍解決，但 settled 沒有改善 |
| 嘗試 2 | 90~95% | 800ms | 1298ms | settled 最短，但肉眼幾乎看不出在跳動 |
| **目前** `c49bc57` | 80~90% | 2000ms | 2513.5ms | 跳動清楚可見，分布集中（9/10 落在 2476~2632ms） |

**發現**

- 起跑點不影響 settled 時間。ease-out 三次方曲線的尾段很平緩，數字在接近 t=1 時才停止變動。彩池金額在百萬級，就算從 90% 起跑，剩下的差值仍有數十萬，所以要縮短動畫時長才有效。
- settled 越短越好和「肉眼感覺得到在跳動」互相衝突。自動化量測只能看前者，最後的版本是實際在瀏覽器觀察後才決定的。

## 風險與後續

- **settled 指標的侷限**：settled 以「連續 300ms 不變」判定。若 hydration 慢於 300ms，腳本可能在動畫開始前就判定穩定，嘗試 1、嘗試 2 的雙峰分布就是這樣產生的。這個指標主要反映動畫時長，不適合當 SSR 效益的依據。
- **產品取捨**：首次揭示時數字會先往下掉約 10~20% 再爬回。若不希望金額出現下降，可以改成首次只用 CSS 做強調效果，只在輪詢拿到新數字時才跑數字動畫。
