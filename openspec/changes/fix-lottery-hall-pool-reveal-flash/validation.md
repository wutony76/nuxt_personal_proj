**誠實結論**：

- 第一版（只改起跑百分比）**沒有解決 settled 時間問題**——ease-out 三次方

- 第一版量測出現的「4 次快、4 次慢」乾淨切分，用固定次數取樣（不依賴
  「連續 300ms 不變」提早中止）的除錯腳本重現同一情境 4 次，結果 4 次都是
  完整的 ~4 秒爬升——證實「快」的樣本是量測腳本本身「連續 300ms 文字不變即
  判定 settled」邏輯的時序巧合（第一次 polling 剛好卡在 `onMounted` 真正
  重置顯示值之前），不是揭示動畫本身真的有時候很快，記錄為量測方法論的
  已知侷限
- 第二版（新增專用的 800ms 短動畫）才真正解決問題：settled 中位數從
  ~4483ms 降到 1298ms，最大值從 ~4550ms 降到 1993ms，視覺上仍保留「從接近
  目標值爬升」的效果（不歸零），兩個目標（視覺修正 + settled 指標不失真）

## 追更：實機觀察「肉眼幾乎感覺不到數字在跳動」

第二版修正（800ms + 起跑 90~95%）雖然讓 settled 指標大幅改善，但直接
在瀏覽器觀察後發現：數字跳動感幾乎消失，看起來就像直接顯示最終值——落差小
（只有 5%~10%）又收得快（800ms），人眼來不及感知變化就已經結束，等於把一
開始要保留的「跳動感」改沒了。

排查過程：

- 先用自動化腳本重現並確認動畫「技術上」確實有在跑（連續取樣能看到數值
  從起點爬升到目標值），排除是程式碼邏輯壞掉
- 分別在匿名訪客與已登入狀態下重新驗證，兩者行為一致，排除是權限狀態造成
  的差異
- 確認是「視覺效果設計本身的取捨」問題，不是 bug：為了把 settled 指標壓到
  最低而把動畫調得太短太小，犧牲了人眼可感知度

修法：`POOL_REVEAL_ANIM_MS` 從 800ms 調整為 2000ms；起跑百分比從
90%~95%（隨機）調整為 80%~90%（隨機）。兩個參數都要同時調整，只調一個
不足以產生明顯的跳動感。

### 視覺驗證（調整後）

Playwright 取樣（每 150ms，共 3 秒）：

```
3,019,623 -> 3,019,623 -> 3,019,623 -> 2,731,732 -> 2,794,850 -> 2,853,368 ->
2,896,454 -> 2,931,161 -> 2,958,970 -> 2,980,118 -> 2,997,094 -> 3,007,433 ->
3,013,987 -> 3,017,648 -> 3,019,227 -> 3,019,620 -> 3,019,623 -> ...
```

數字從 3,019,623 明顯下探到 2,731,732（約下探 9.5%），再花約 2 秒平滑爬回
目標值，有 13 個以上可辨識的中繼取樣值，跳動感清楚可見。

### 效能重新驗證

`test/perf-ssr-lottery-hall.mjs`，10 次樣本：

| 版本 | settled 中位數 | 樣本分布 |
|---|---|---|
| 800ms + 90~95% | 1298ms | `[1993,264,276,212,255,1394,1302,1294,1754,1309]`，有雙峰傾向 |
| 2000ms + 80~90%（最終版） | 2513.5ms | `[2632,2483,2525,2511,2499,2550,2516,2476,2929,2482]`，9/10 集中在 2476~2632ms，無雙峰 |

**誠實結論**：2000ms + 80~90% 的 settled 時間（~2.5 秒）比最初從 0 起跑、
沿用 4000ms 的版本（~4.4 秒）快將近一半，同時分布遠比 800ms 版本穩定集中
（不再出現雙峰）。代價是比 800ms 版本的 settled 時間慢，但這是刻意的取捨：
「settled 指標快」與「人眼感覺得到在動」互相拉扯，不能只優化其中一個指標
而犧牲另一個，2000ms + 80~90% 是實機觀察後選定的折衷點。
