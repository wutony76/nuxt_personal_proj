### 來源沒有的資訊（判定門檻與五行對應）

`liangmian/play_script.js` 全篇（判定式在伺端）只做「組裝 `playId`/`buyCode` 送出」，
沒有任何和值/上下盤/奇偶盤/五行的計算邏輯；bglottery 本身也沒有 kl8 的走勢頁可供比對特徵字樣。
額外查證 bglottery 內其他彩種的「五行」先例（六合彩 `6hc/config/dict.js` 的個別號碼歸類表）發現：
本專案 `shared/config/6hc-cd.ts:56-68` 已明確判定「用 `n % 5` 做號碼分組」是六合彩五行的**誤用**
（正確定義是逐年輪轉的納音五行），且六合彩的判定模型是「單一特碼的屬性」，
與 kl8「20 顆開獎號的集合特徵」在結構上本來就不同——**不能把 6hc 的五行模型套到 kl8**。

因此以下四項門檻與定義由使用者於提案階段拍板（記錄於本檔，實作時全部收斂成具名常數）：

| 項目 | 拍板結果 | 依據 |
|---|---|---|
| 和值大小分界／810 特例 | **≥810 大、<810 小，無和局**（810 併入大） | 比照 kl10 的「無和局」慣例；`liangmian` 8 項本身沒有「和」項，內部證據吻合 |
| 上下盤 | **1~40 為上盤、41~80 為下盤，比個數多寡，10:10 為和盤**（改名「上下和」避免與奇偶盤撞名） | 與 kl10 上下盤模式一致；`liangmian` 該組恰有 3 項（上/和/下），結構吻合 |
| 奇偶盤 | **比奇數/偶數個數多寡，10:10 為和盤**（改名「奇偶和」） | 同上，該組恰有 3 項（奇/和/偶） |
| 五行邊界 | **20 顆總和依機率窮舉的等機率五等分**：金≤734／木735~787／水788~833／火834~886／土≥887 | 外部 Keno 規則站給的區間（210~695 等）機率明顯不均，與本專案「賠率一律窮舉推導」慣例不合，改用 DP 窮舉出的等機率邊界 |

其餘門檻沿用本專案既有慣例，不另發明：
- 任選判定＝「選中號碼是否全部落在 20 個開獎號內」（與 kl10 同架構類推，任選判定式本身在伺端查無實據，
  但與 kl10 當年遇到的狀況完全相同，沿用同一結論）

## Goals / Non-Goals

**Goals:**
- 依 `kl8.ts`（機率核心）→ `kl8-cd.ts`（判定＋賠率＋爆池＋選號彩池玩法）→ `kl8cd/{plays.js,helpers.ts}`
  （看板設定）→ `server/.../kl8.ts`（單一信用盤 service）→ `useKl8.ts` → `components/lottery/bg/kl8/**`
  → `pages/lottery/bg/kl8.vue` 的分層，完整複刻 EGGS／KL10 一套。
- 賠率一律「公平賠率（母數 ÷ 命中數）× RTP」推導，不寫死拍板數字。
- 爆池接既有 `shared/config/jackpot.ts` 骨架，weight 以「設定檔宣告 → 結算反查」關聯玩法。
- 選號彩池玩法比照 `add-pool-play` 已建立的模式（EGGS／KL10 各一種），同步擴充到 KL8。

**Non-Goals:**
- 不建立官方盤（OF）、不建 `kl8Shared.ts`（沒有共用對象）。
- 不實作色波（來源殘留檔，kl8 無此玩法）。
- 不改動既有彩種（含 EGGS／KL10）的判定與結算邏輯，僅將 `pool-play` 能力擴充到 KL8 一項新遊戲。

## Decisions

### 1. 母數三種，且母數本身超出 `Number.MAX_SAFE_INTEGER`——這是 kl8 與 kl10 最大的差異

| 判定對象 | 母數 | 用在 |
|---|---|---|
| 單一號碼是否入選 20 顆開獎號 | `C(80,N)` / 對應命中組合數 | 任選各分頁 |
| 兩區個數對比（1~40 vs 41~80，或奇數 vs 偶數，各 40 個） | `C(40,k)×C(40,20-k)` | 上下盤、奇偶盤、爆池 |
| 20 顆的**集合**性質（總和） | `C(80,20) = 3,535,316,142,212,174,320` | 和值、五行 |

⚠️ **`C(80,20)` ≈ 3.535×10¹⁸，遠超過 `Number.MAX_SAFE_INTEGER`（9,007,199,254,740,991 ≈ 9×10¹⁵）**，
比 kl10 的 `C(20,8)=125,970` 大了 13 個數量級。這意味著：
- 不能像 `kl10SumCounts()` 那樣「遞迴窮舉組合本身」建表（kl10 是 125,970 條路徑，kl8 是 3.5×10¹⁸ 條，
  不可能真的窮舉每一種組合）。
- `kl8SumCounts()` 必須改用**動態規劃（子集和卷積）**：`dp[j][s]` = 從 1~80 選 `j` 個號碼、總和為 `s`
  的方法數，逐號碼 `n=1..80` 累加更新（標準 0/1 knapsack 計數 DP），`j` 上限 20、`s` 範圍 210~1410。
  DP 規模約 `80 × 20 × 1200 ≈ 190 萬`格更新，**全程用 `BigInt`**（本次驗證已用此法窮舉，
  `dp[20]` 加總與 `C(80,20)` 完全吻合，見下方機率表）。
- 上下盤／奇偶盤／爆池不需要 DP，直接用組合數閉式解 `C(40,k)×C(40,20-k)`（比照 kl10 的
  `kl10HalfSplitCounts()`），這個規模只到 `C(40,20)`（≈1.4×10¹¹，仍超出安全整數範圍但單次計算量小，
  可用 BigInt 直接算）。
- `kl8SumCounts()` 只回傳整數計數（`dp[20][s]`），一個 process 只算一次（memoize），
  不保留任何組合陣列本身。

### 5. 任選複式展開放在前端 composable（比照 kl10）

來源 `renxuan/play_script.js` 就是在前端把「已選 k 個號碼」展開成 `C(k, N)` 注再送單。
本專案沿用同一個切法：`useKl8` 的 `fetch.betsRenxuan()` 產生組合、每個組合一注，
伺端仍是「一注一注驗、一注一注派彩」，`orders.ts`／`settleIssuePrize()`／爆池分配完全不用改。

### 6. 爆池：接骨架，不新發明

- 觸發條件「奇偶個數其中一側 ≤5 或 ≥15」＝ 66,366,308,138,029,536 / 3,535,316,142,212,174,320
  ≈ 1.8772%，與 kl10 奇偶≥7/8（1.9767%）、6hc 特別號開49（2.04%）同量級。
- 不挑一個現成注項當條件：kl8 沒有 kl10 的「特別號」概念，任選的固定命中率屬於**注單**性質
  （任何一期都必然存在對應組數的中獎任N中N），不能當開獎特徵。
- 用奇偶而非上下：兩者機率完全相同（結構對稱，皆為兩個 40 元素池的個數分佈），
  但奇偶只依賴號碼本身的奇偶性，不依賴任何門檻常數（上下依賴 1~40/41~80 這條半分線），
  與 kl10 選奇偶而非上下的理由一致。
- 沒有「雙重加成」問題：此條件不對應任何單一注項（上下盤/奇偶盤的「奇偶和」是 10:10 全等，
  跟「≤5 或 ≥15」完全不重疊），`kl8cd/plays.js` 不需要任何 `weight: 0` 排除。

### 7. 選號彩池玩法：擴充既有 `pool-play` 能力到 KL8（比照 `add-pool-play` 的設計模式）

`add-pool-play` 已確認 K3-OF 的分層派彩機制（`match/type/ratio/minAmount/name`）本身就是本專案
自己設計的機制，不是從來源找規則；EGGS／KL10 已依此模式各建立一種「選號」彩池玩法。
KL8 同步擴充，設計為**選 3 個號碼（1~80，不重複）**，依命中顆數對照 `KL8_POOL_PRIZE_TIERS` 分層：

| 命中顆數 | 機率（`C(20,k)×C(60,3-k)/C(80,3)`，`C(80,3)=82,160`） | 對應層 |
|---|---|---|
| 3（全中） | 1,140 / 82,160 ≈ 1.3874% | 頭獎（`type: 'pool'`，`ratio` + `minAmount` 保底） |
| 2 | 11,400 / 82,160 ≈ 13.878% | 二獎（`type: 'pool'`，`ratio`） |
| 1 | 35,400 / 82,160 ≈ 43.086% | 三獎（`type: 'fixed'`，固定倍數，比照 kl10 的 match2） |
| 0 | 34,220 / 82,160 ≈ 41.649% | 不派彩 |

選 3 碼頭獎機率 1.3874% 與 KL10 選 4 碼頭獎機率 1.445%（`C(8,4)/C(20,4)`）幾乎同量級——
比選 4 碼（`C(80,4)` 分母，頭獎機率僅 0.3064%，與 KL10 差 4.7 倍）更貼近既有先例，故採選 3 碼。
比照 `KL10_POOL_PRIZE_TIERS` 的三層結構（`pool`/`pool`/`fixed`）、`KL10_POOL_FLOOR` 的池底重骰邏輯、
`KL10_POOL_RAKE_RATIO`（2%，與既有爆池 1% 並行的另一條抽水線）。

⚠️ 選 3 碼任一組合的命中分布完全相同（開獎本身 20 顆不重複、無「選型影響機率」的落差，
與 KL10 選 4 碼同理，比 EGGS 選 3 位可重複數字更乾淨）。
⚠️ 此玩法**不進** `kl8cd/plays.js` 看板網格（比照 K3-OF 的 `xuanhao`／KL10 的 `KL10_POOL_PLAY_KEY`），
伺端驗證用硬編碼 `KL8_POOL_QUOTA`；查不到看板 weight，給 `KL8_POOL_PLAY_WEIGHT` fallback 常數，
讓這個玩法的注單也能參與現有爆池分配。
⚠️ 兩個池（爆池／選號彩池）完全獨立：各自的池底／抽水／滾存互不影響，只是同一筆下注會依
`KL8_JACKPOT_SETTINGS.rakeRatio`（1%）與 `KL8_POOL_RAKE_RATIO`（2%）**分別**抽水進兩個池。

### 8. 元件目錄不分 `cd/`／`of/`；任選、選號各自另開一支看板

依 `openspec/project.md` 的分層標準，kl8 永遠只有一個盤口，元件平鋪在
`app/components/lottery/bg/kl8/{base,block,block/footer}/`。與 EGGS 不同的是多兩支元件：
- `base/BoardRenxuan.vue`：任選選號池 → 組合展開，互動模型與「一注項一金額」的表格看板不同
- `block/PoolPicker.vue`：選號彩池玩法，比照 `k3/of/block/Picker.vue`／KL10 的 `PoolPicker.vue`

## Risks / Trade-offs

- **[Risk]** 和值大小分界、上下盤／奇偶盤定義、五行邊界、爆池條件、選號彩池碼數皆為使用者拍板，
  非原始碼直接依據（判定式在伺端）。
  → **Mitigation**：全部收斂成 `shared/config/kl8.ts` 的具名常數（`KL8_SUM_BIG_LINE`、
    `KL8_HALF_LINE`、`KL8_WUXING_BOUNDS`、爆池門檻 `KL8_JACKPOT_LOPSIDED_MIN`）並附「使用者拍板」註解，
    改一處即全站生效；且每個門檻皆有機率窮舉數字佐證量級合理，非隨意數字。
- **[Risk]** `C(80,20)` 超出 `Number.MAX_SAFE_INTEGER`，若誤用一般 `number` 做窮舉／建表會在極端情況
  精度失真（尤其是 `dp[20][s]` 這類大數加總）。
  → **Mitigation**：`kl8SumCounts()`／`kl8HalfSplitCounts()` 全程用 `BigInt`；對外回傳機率時才轉型成
  `Number`（機率本身是 0~1 的小數，不受精度問題影響，只有中間的整數計數需要 `BigInt`）；
  單元測試需覆蓋「`dp[20]` 加總 `=== C(80,20)`」這個對帳項。
- **[Risk]** `kl8SumCounts()` 的 DP 建表規模（80 × 20 × 1200 ≈ 190 萬格 BigInt 更新）比 kl10 的遞迴組合
  窮舉（125,970 條路徑）大上一個量級，需注意模組載入時的計算時間。
  → **Mitigation**：memoize，一個 process 只算一次；DP 只保留 `dp[j][s]` 計數陣列（21×1411 個 BigInt），
    不展開任何組合本身，記憶體佔用遠小於窮舉組合。
- **[Risk]** 任選複式展開在前端 → 惡意端可送出任意注碼組合；複式一次可能展開很多注
  （例如任二中二選 8 個號碼 = 28 注），單注限額過得去但總額暴增。
  → **Mitigation**：伺端 `validateBetQuota()` 對每一注都跑 `kl8HasBetCode()`（含判定層的號碼驗證），
    任一注不合法整筆拒單；賠率由伺端用 `kl8TabOddsOf()` 重算後才鎖進注單；
    沿用既有「單期分頁上限」（`settings.quota.issue.max`）擋總額；前端送單前顯示注數與總額。
- **[Risk]** 選號彩池玩法與既有爆池是兩條獨立的抽水線，容易在結算時誤把兩池的 `carry`/`issueMap`
  混用（比照 `add-pool-play` 對 EGGS／KL10 的提醒）。
  → **Mitigation**：`server/services/game/lottery/bg/kl8.ts` 內兩組狀態各自命名清楚
  （`issueJackpotMap`/`carryJackpot` vs `issuePoolMap`/`carryPool`），並在單元測試各自對帳。

## Migration Plan

全新彩種，無既有資料需要遷移。步驟：
1. 依 `tasks.md` 由 config → server → 前端依序實作，每層各自驗證
   （esbuild + node 對帳腳本、curl、`npm run dev`）
2. 全部完成後跑一次端到端：登入 → 任選／兩面／選號彩池玩法各下注 → 等開獎 → 對帳派彩、
   爆池抽水／滾存、選號彩池抽水／滾存
3. 中止時可直接刪除新增檔案，並回退 `constants.js`／`storage.ts`／`api.ts`／`lottery-hall.vue`／
   `BgAutoPanel.vue`／`useBgAutoActive.ts` 的追加段落（皆為追加式修改）
