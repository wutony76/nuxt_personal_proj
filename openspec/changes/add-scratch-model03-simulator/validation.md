## 功能驗證

### API 層（`test/test-scratch-model03.mjs`，12 項全過）

```
── 拒絕不合法的目標金額 ──
  ✔ 不合法目標金額（999）→ 400

── 試算張數上限/下限夾擠 ──
  ✔ count=0 夾擠成至少 1 張
  ✔ count=999 夾擠成上限 50 張

── 機率表消費邏輯一致性（目標金額 1500，跑 30 張覆蓋足夠樣本） ──
  ✔ API 回 200
  ✔ 回傳 30 張卡
  ✔ 每張卡都有 5 局
  ✔ 每張卡的 winCoin 都等於輸入的目標金額
  ✔ getCoin 只在雙方手勢相同（平手）時才為非零值，且剛好等於 coin 的一半
  ✔ 150 局樣本內，至少出現過一次非零 getCoin

── 目標金額 0 ──
  ✔ 目標金額 0 仍正常回應
  ✔ 目標金額 0 時每局面額皆為顯示用隨機值、getCoin 皆為 0
```

過程中抓到一個真實 bug：`count=0` 原本會被 `Number(body?.count) || 10`
誤判成「沒填」、蓋成預設值 10（`0` 在 JS 是 falsy 值），已修正為用
`Number.isFinite()` 判斷。

### 人工抽樣核對（API 直接呼叫，確認「顯示面額加倍」這個容易忽略的細節）

目標金額 1500、count=3 的樣本中，有一局顯示「石頭 vs 石頭」（手勢相同，
平手）、`coin: 200`、`getCoin: 100`——追查確認：這局實際觸發的原始面額是
100（平手 40% 機率分支，100 是唯一會真的走隨機的面額），顯示面額依規則
乘以 2 變成 200，`getCoin` 是顯示面額的一半（100），不是原始面額的一半——
確認跟 Python 原始碼邏輯一致，不是移植錯誤。

## 追加驗證：OpenCV 精確量測取代肉眼比對

### 手勢圖示（`HAND_POSITIONS`）

用 OpenCV Hough circle transform 偵測 `card-base.jpg` 上 10 個手勢圈圈的
精確圓心像素座標，寫 Playwright 腳本程式化比對渲染結果：

| 局數 | myHand 誤差 | enemyHand 誤差 |
|---|---|---|
| 1~5 | 0.0px | 0.0px |

### 金額文字框（`COIN_CENTER_OFFSET`）

裁切放大底圖 5 局分別量測框的實際中心點，程式化比對：

| 局數 | 誤差 |
|---|---|
| 1 | (-1.0, -1.0) |
| 2 | (0.0, -1.0) |
| 3 | (0.0, -2.0) |
| 4 | (-1.0, 1.0) |
| 5 | (1.0, 1.0) |

全部在 ±2px 內（圈圈半徑 ~35px，文字框約 24~89px 寬），視覺上與使用者
提供的參考截圖一致。

### 容器響應式縮放

實測 1440px 與 480px 兩種視窗寬度（`.smc` 容器分別渲染成 600px 全寬與
364px 縮放寬度），座標換算成百分比後兩種寬度下對齊皆正確，無視窗寬度
相依的跑位問題。
