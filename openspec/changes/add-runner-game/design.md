## Context

- `add-game-history` 已建立 game-hall 小遊戲的完整架構：client 頁面自包含（engine class + ref/reactive 鏡像 snapshot）＋ `useGameHistory`（A/B 雙模式：未登入 localStorage／已登入 server API）＋ server 端 `RETRO_GAME_BASE`（共用基底＋每款遊戲一個服務檔＋每款遊戲一組 API 路由資料夾）。
- 現有六款遊戲裡，snake／racing／tetriminos／match3rush／match3classic 都是「單次連續衝分」玩法（撞到／時間到／步數用完就結束，`score` 是原始表現值，開放式無上限）；只有 PONG 是本次架構唯一的例外（多局賽制、`score` 定義為勝場數）。RUNNER 屬於前者這一類，架構上直接比照 racing.vue／snake.vue 的既有慣例，不需要引入 PONG 那套局數/賽制邏輯。
- `racing.vue` 是最接近的既有參考：以「存活 tick 數」計分、開放式無上限、`coinRate: 0.5`／`maxReasonableScore(): 5000`；RUNNER 的「存活距離」在數值量級與計分哲學上與此相同，可直接沿用同一套校準邏輯，而不必像 match3／PONG 那樣重新估算。
- 專案目前沒有任何遊戲是「側視角＋垂直方向迴避（跳躍／下蹲）」的操作模式（snake 是四方向移動、racing 是水平換道、tetriminos 是方塊操作、match3 是點擊交換、pong 是垂直移動球拍）；RUNNER 引入的「固定水平位置＋垂直方向二元迴避」是全新的操作手感，但底層仍是既有的 tick 驅動 engine class 慣例，不需要新的架構模式。

## Goals / Non-Goals

**Goals:**
- 提供一款經典側視角跑酷玩法：固定角色＋自動捲軸＋跳躍／下蹲雙操作，撞到障礙物即結束。
- 分數（存活距離）開放式無上限，難度（捲動速度、障礙密度）隨距離自動提升，比照 snake/racing/tetriminos 既有的 Lv 慣例。
- Server 端、client 資料層、game-hall 入口完全比照既有六款遊戲的慣例逐一擴充，不引入新的架構模式（例如不新增資料庫、不新增配對系統）。

**Non-Goals:**
- 不做左右換道／多車道（維持單一車道，只有跳躍／下蹲兩種迴避動作）。
- 不做道具收集（金幣／加成道具等）、不做角色外觀切換。
- 不做多人對戰或排行榜。
- 不引入資料庫；server 端持久化沿用專案現況的 in-memory 作法。
- 不做遊戲重播、不儲存完整過程，只存結算後的摘要（分數、等級、時間等）。

## Decisions

1. **單人連續衝分玩法，比照 snake/racing/tetriminos/match3 既有慣例，而非 PONG 的多局賽制**
   - 理由：使用者這次沒有提出局數／回合的需求；「跑酷」這個 genre 本質上就是「一次連續嘗試，直到失敗為止」，符合玩家對這類遊戲的既有預期，也符合本專案現有六款遊戲中佔多數的既有模式（PONG 才是特例）。
   - 做法：`score` 定義為存活距離（開放式無上限），比照 racing.vue 的「原始表現值」語意，`useGameHistory` 的呼叫方式與其他四款單次衝分遊戲完全一致。

2. **單一車道，只有跳躍／下蹲兩種操作，不做左右移動**
   - 理由：經典側視角跑酷（Chrome Dino、Canabalt）的核心樂趣在「時機判斷」而非空間移動；維持核心玩法純粹，也讓碰撞判定簡化成「地面障礙的頂部高度」與「空中障礙的底部高度」兩種二元判斷，不需要處理左右方向的空間碰撞。
   - 替代方案：仿 Subway Surfers 式三車道＋左右切換——放棄，這會讓 RUNNER 跟現有 racing.vue（水平換道躲避）在操作手感上高度重疊，失去新增這款遊戲的差異化意義。

3. **跳躍採輕量重力 physics（比照 PONG 球體 tick 積分速度的做法），下蹲採二元狀態（非 physics）**
   - 理由：跳躍需要有自然的拋物線弧度（起跳→上升→下降→落地），沿用 PONG 已經建立的「每個 tick 對速度做積分更新位置」慣例，維持專案內「有連續運動的機制都用相同的簡易 tick physics 手法」的一致性；下蹲則只是暫時性的角色碰撞箱變矮（沒有位移曲線可言），做成二元狀態（按住＝下蹲中）更直觀，也比照 snake 既有的按鍵狀態（`upHeld`/`downHeld` 風格）處理。
   - 做法：跳躍時角色 `y` 速度受重力（`GRAVITY` 常數）逐 tick 遞減／遞增直到落回地面基準線；下蹲純粹是碰撞箱高度切換，無獨立 physics。

4. **障礙物分兩類（地面／空中），出現頻率與間距隨等級調整；等級判定沿用既有 Lv 慣例**
   - 理由：兩種障礙給玩家「跳／蹲」兩種決策，隨距離增加混合出現、間距縮短，提供跑酷應有的「反應時間越來越短」壓力曲線；等級／難度判定方式直接比照 snake/racing/tetriminos 既有的「依分數門檻分級」做法，不引入新的難度模型。
   - 做法：障礙物以固定初速（等於當前捲動速度）由畫面右側生成、往左移動，超出畫面左側即回收；生成間隔與地面/空中障礙比例依當前等級調整（等級越高，間隔越短、空中障礙比例越高，混合出現的組合越刁鑽）。

5. **碰撞判定：以角色固定 x 範圍 + 障礙物 x 範圍是否重疊，重疊時再比對垂直方向是否閃避成功**
   - 理由：因為車道固定（水平位置不變），碰撞判定只需要處理「障礙物是否進入角色的 x 範圍」與「角色當下的垂直狀態（站立／跳躍中／下蹲中）是否閃避掉該障礙物的垂直佔位」，比 PONG 的球拍矩形相交判定更單純。
   - 做法：地面障礙只有站立或下蹲時會撞到（跳躍時角色 y 高於地面障礙頂部即安全）；空中障礙只有站立或跳躍時會撞到（下蹲時角色碰撞箱矮於空中障礙底部即安全）。

6. **Coin 倍率：直接比照 `racing.ts` 既有校準（`coinRate: 0.5`、`coinCapPerRun: 300`、`coinDailyCap: 100000`、`maxReasonableScore(): 5000`）**
   - 理由：RUNNER 與 racing 同屬「開放式無上限、以存活時間/距離為分數」的計分哲學，數值量級預期相近（皆是「跑越久分越高」），不需要像 match3／PONG 那樣重新估算全新的常數；沿用既有校準也降低上線後失衡的風險（racing 這套倍率已經跑過一段時間、相對穩定）。
   - 若上線後實測發現 RUNNER 的分數成長速度跟 racing 有明顯落差，可獨立調整 `runner.ts` 的常數，不影響其他遊戲。

## Risks / Trade-offs

- [風險] 跳躍／下蹲的碰撞判定若寬容度抓太緊，會讓玩家覺得「明明跳過去了還是算撞到」，體驗變差 → [因應] 角色與障礙物的碰撞箱刻意抓得比視覺圖形略小（比照多數平台跳躍遊戲的寬容判定做法），且此為可獨立調整的常數，不影響整體架構。
- [風險] 障礙生成間隔／捲動加速曲線是程式碼估算值，可能太快（很快就死）或太慢（拖很久才有挑戰性）→ [因應] 比照 racing/match3 既有做法：先讓機制跑起來，上線後依實測調整常數，不影響資料層與對外介面設計。
- [風險] 沿用 racing.ts 的 coin 倍率是假設兩者分數量級相近的推測，若實測差距明顯會造成「這款遊戲比較好賺／比較難賺」→ [因應] `coinRate`／`maxReasonableScore` 是獨立於 RUNNER 服務檔的常數，之後可單獨校準不影響其他遊戲。

## Migration Plan

- 全新功能，無既有資料需要遷移，且刻意設計成獨立的 `gameKey`，不影響既有六款遊戲的紀錄與 coin 上限。
- 部署順序（每一步都可獨立回滾，比照既有幾次擴充的分步策略）：
  1. Server 端服務層與 `storage.ts` 註冊（尚未被路由引用，無風險）
  2. Server 端 API 路由（存在但尚未被前端呼叫，無風險）
  3. Client `app/services/api.ts` 擴充
  4. `useGameHistory.ts` 擴充
  5. 遊戲頁面 `app/pages/game/runner.vue`（此步驟起才有實際資料寫入行為）
  6. `game-hall.vue` + `GameMachineCard.vue` + `GameHistoryDialog.vue`（此步驟起使用者才看得到入口，是唯一改變可見行為的步驟）

- 是否要幫 RUNNER 額外設計「連續閃避 combo」加分（比照 match3 的連鎖加成概念）？本次先不做，維持單純的距離計分，若後續想強化正向回饋可再評估。
