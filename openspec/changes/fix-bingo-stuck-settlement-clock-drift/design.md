# Design

## 兩套互相獨立、校正能力不對等的狀態追蹤

`BingoClass` 同時維護兩種「目前到哪了」的狀態，各自用不同依據判斷：

1. **`lastKnownOfficialPeriod`**（期別序號追蹤）：每次輪詢都直接跟「剛從
   官方 API 拿到的最新一期序號」比對，不同就表示有新資料。這個判斷不依賴
   任何內部累積的時間/計數器，純粹是「跟外部真相比對」，所以不管中間停擺
   多久，下次輪詢只要官方 API 正常回應，立刻就能知道「現在外部真正是哪一
   期」，天然具有自我校正能力。

2. **`drawAt`／`cutoffAt`**（開盤/結算時間窗）：修正前的算法是
   `_nextFiveMinuteBoundary(new Date(this.drawAt + 1000))`——「從上一次記錄
   的內部時間」往後推 5 分鐘。這是跟「自己過去的狀態」比較，不是跟外部真相
   （真實時間）比較。一旦 `this.drawAt` 因為任何原因落後真實時間，之後每次
   推算都只是在錯誤的基準上繼續疊加，永遠不會自動對齊回真實的「現在」。

兩者的差異在於：**序號比對的對象是「外部當下的真相」，時間推算的對象卻是
「自己的歷史」**。前者天然可以自我修復，後者則會把任何一次偏差永久放大/
鎖死。

## 什麼情境會觸發

本機開發環境最常見的觸發情境：筆電闔蓋休眠一段時間後喚醒。Node process 被
作業系統掛起時，`server/plugins/init.ts` 的全域排程（每 300ms 呼叫一次
`circle()`）完全不會執行，`this.drawAt` 會停在休眠前的那個值不動。喚醒後，
`circle()` 恢復執行，`_ensureIssue()` 讀到的 `now` 已經是喚醒後的真實時間，
遠晚於停滯的 `cutoffAt`，於是立刻判定「已過開獎時間」進入「結算中」——這本身
沒問題，是正確反應。問題在於之後每次成功結算，`drawAt` 只從「休眠前的那個
落後值」往後推 5 分鐘，不會往「真實現在」對齊，所以落後的時間差被原封不動
地延續到每一個後續週期，永久卡住。

（正式環境的長駐 server 理論上較少遇到這種整段時間完全無法執行程式碼的情境，
但任何讓 event loop 長時間被阻塞或程序被暫停的狀況——例如部署平台的休眠/
喚醒機制、容器被暫停等——都可能觸發同一個根因。）

## 修法：一律用真實 `now` 當基準

```ts
const drawAt = _nextFiveMinuteBoundary(now).getTime()
```

`_attemptSettlement(now: Date)` 本身已經把「這次結算當下的真實時間」當成
參數傳進來（`circle()` 呼叫時傳的就是 `MEMORY.now`），不需要另外取得。改用
這個 `now` 取代 `this.drawAt + 1000`，讓每一次成功結算都重新對齊到「真正
現在的下一個 5 分鐘整點」，不管中間累積了多少次暫停／延遲，下一輪詢週期
就能立刻恢復正常。

這跟 `_ensureIssue()` 在「完全沒有任何已知狀態」時的 bootstrap 路徑
（`const drawAt = _nextFiveMinuteBoundary(now).getTime()`）用的是同一個
基準、同一個函式呼叫方式，修正後兩條路徑在「要不要信任自己過去的狀態」這件
事上的立場一致，不再互相矛盾。

## 沒有處理的部分：既有的期別序號超前量

`currentIssue` 的期別序號在這個 bug 存在期間，已經因為 `_laterOfficialPeriod()`
「取較大值」的邏輯，被意外推到比真實官方序號超前了約 91 期。這個超前量是
過去事件遺留下來的既成狀態，序號本身只是顯示用的標籤，不影響下注/結算/
派彩邏輯的正確性（`_attemptSettlement` 不要求序號要跟官方對齊，只要求
「拿到的官方期別字串」跟「上次記錄的不同」就會結算）。本次修正後，
`currentIssue` 不會再繼續被推得更超前，但不會回頭修正已經累積的這 91 期
落差——如果需要讓顯示的期別序號重新對齊官方真實序號，需要另外評估（例如
手動重設內部序號基準），不在本次範圍內。
